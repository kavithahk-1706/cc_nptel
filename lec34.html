Fog Computing – II

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Continues fog computing with a structured cloud-vs-fog comparison, key use cases (connected vehicles, smart grid, disaster management, IoT), and a detailed treatment of resource management challenges in fog networks. Important for exam questions on fog vs. cloud differences and resource management problems.

1 · Cloud vs Fog — Comparison
AttributeCloudFog
LatencyHigh (multi-hop to remote datacenter)Low (one hop, edge of network)
Delay jitterHighVery low
Server locationWithin the Internet (user often doesn't know exactly where)At the edge, local network — known and localized
Client-to-server distanceMultiple hopsOne hop
SecurityUndefined (user has little control over third-party cloud)Can be defined — organization may control local fog devices
Attack on data en routeHigher risk (many hops = more interception points)Lower risk (single hop)
Location awarenessMinimalHigh — fog is inherently location-aware
Geographic distributionLogically centralized (few datacenters)Highly distributed (many edge nodes)
Number of server nodesFew, but extremely resourcefulVery large number, lower resources per node
Mobility supportLimitedBetter — local decision-making handles mobility transitions
Real-time applicationsSupported, but with higher latencyPrimary motivation — low-latency real-time support
Last-mile connectivityUsually wired/cableUsually wireless
Relationship: Cloud and fog are complementary, not competitive. Proper orchestration and synchronization between fog (local, real-time) and cloud (global, compute-heavy) is what makes the combined system successful.
2 · Fog Use Cases
Emergency / Disaster
Emergency evacuation systems
During fire/earthquake, default exit routes may be blocked. Fog nodes dynamically re-plan exit routes using real-time sensor data (per room, per floor) without cloud round-trip. Also: real-time landslide/flood notifications to affected areas.
Connected Vehicles (VANET)
Vehicle-to-vehicle / vehicle-to-infrastructure
Road-side units (RSUs) and access points form the fog layer. Accident alerts, infotainment, traffic support handled locally. V2V collision warnings cannot wait for cloud round-trips — fog enables sub-second response. Traffic lights adapt signal timing to congestion in real time.
Smart Grid
Power management
Smart meters at each home report consumption. Fog layer aggregates per-building/campus usage and makes local provisioning decisions. Aggregated data sent to cloud for long-term analytics (monthly patterns, regional provisioning).
IoT / Sensor Networks
Data pre-processing and aggregation
Large sensor deployments produce raw data streams too large to transmit in full. Fog pre-processes, compresses, and summarizes data before forwarding to cloud — reduces core network congestion and cloud processing load.
3 · Resource Management in Fog Networks
Core tension: Fog devices are resource-constrained compared to cloud servers. Achieving the cloud's scalability, high availability, and latency guarantees on limited fog hardware is the central resource management challenge.

Resource management problem dimensions

Utilization
Idle node exploitation
Some fog nodes may be overloaded while others are idle (skewed distribution). Need to utilize idle nodes for better throughput through load balancing and parallel operations.
Load balancing
Meeting real-time delay requirements
Real-time applications have strict latency SLAs. Load must be balanced so no node becomes a bottleneck that violates timing guarantees.
Fault tolerance
Node failure handling
If a fog node goes down, applications and data on it must migrate. Need: fault detection, migration triggers, target node selection, migration of partially processed data — all with minimal latency impact.
Scalability
Scaling fog infrastructure
Scalability is a core cloud property that fog must also support. As the number of IoT devices grows, fog must scale gracefully without centralized coordination bottlenecks.

Specific operational challenges

ChallengeDescription
Data unavailabilityApplication runs on a fog node but required data lives on a different sensor/source — data fetching adds latency
Node overloadExecuting fog node becomes unresponsive under heavy workload, compromising latency guarantees
Migration target selectionWhen a node fails, choosing the new node quickly and correctly is non-trivial — nearest node may not be the most suitable
Partial state migrationPartially processed persistent data must be migrated to a new node while maintaining correctness
Result deliveryFinal result must reach the client/actuator within the latency deadline even during migration
Multi-tenancy isolationMultiple applications may collocate on the same fog node — data and resource integrity of each must be ensured; fog has fewer resources than cloud, making isolation harder
Component placementDeploying application components across different fog nodes while meeting each component's latency requirement

4 · Security Challenges Specific to Fog
Resource-constrained security: Resource-hungry security measures (encryption, intrusion detection) that run fine on cloud servers may not be deployable on lightweight fog devices. Security mechanisms must be sized for fog hardware.
Attack surface
Fog as attack platform
Distributed fog nodes — each with less oversight than centralized cloud — can be exploited to launch attacks (DDoS, man-in-the-middle). Less centralized control = more potential entry points.
Robustness
Fog device robustness
How hardened are fog devices? Physically accessible edge devices (road-side units, smart meters) are easier to tamper with than datacenter servers in secured facilities.
Summary
Cloud vs Fog: Fog wins on latency, location awareness, and real-time capability; cloud wins on compute power and scalability. The two must be orchestrated together.
Key use cases: Connected vehicles (VANET), smart grids, disaster management, and IoT sensor networks — all require local, real-time processing that cloud round-trips cannot support.
Resource management: The core operational challenge — load balancing, fault tolerance, migration of partial state, multi-tenant isolation, and real-time latency guarantees on constrained hardware.
Security: Distributed fog creates a far larger and harder-to-control attack surface than centralized cloud. Resource-constrained fog nodes may not support heavy security measures.
Bottom line: Fog is a necessity for IoT-scale, real-time applications. Its success depends on proper orchestration with cloud — not a replacement, but a companion computing layer.
