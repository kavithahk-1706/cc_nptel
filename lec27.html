Lecture 27 HIGH priority

Cloud Security II — Cloud-Specific Risks & Gartner's Seven Parameters

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Covers what makes cloud security different from traditional enterprise security (co-tenancy, lack of control, reputation fate sharing), Gartner's seven cloud security risk parameters (including RPO/RTO for recovery), and hypervisor, access control, application, and data lifecycle threats. Gartner's seven and the hypervisor threat model are high-probability exam topics.

1 · Why Cloud Security Is Different
Co-tenancy
Multiple independent users share the same physical infrastructure. An attacker can legitimately lease the same physical machine as the target — no need to break in. Traditional security assumes attackers are outsiders.
Lack of control
Customer data, applications, and processes reside on the provider's premises. The consumer has no direct control over the underlying infrastructure — only indirect control through SLAs.
Reputation fate sharing
If a co-tenant is involved in malicious activity (spam, botnet), the shared IP range may be blacklisted, affecting all tenants on that infrastructure — even innocent ones.
Cloud adds to traditional CIA threats: Cloud is still subject to confidentiality, integrity, availability, and privacy attacks — plus the three cloud-specific challenges above. This is the primary reason organizations remain reluctant to fully migrate mission-critical workloads to cloud.
2 · Responsibility Shift by Service Model
As service model moves IaaS → PaaS → SaaS, provider responsibility increases and consumer responsibility decreases. Under IaaS, the consumer manages everything above the infrastructure; under SaaS, only data handling remains the consumer's concern. Security posture must be matched to the chosen service model.
3 · Gartner's Seven Cloud Security Risk Parameters
#Risk parameterKey concern
1Privileged user accessSensitive data processed outside the enterprise is handled by provider admins. Consumers lose physical, logical, and personnel controls. Ask providers: how are privileged admins hired, overseen, and access-controlled?
2Regulatory compliance & auditTraditional IT undergoes external audits; cloud providers may not permit customer audits. SLA tries to address this but gaps remain. No customer-side audit facility; difficult to verify compliance of data held outside the organization. Trusted third-party auditors may be required.
3Data locationConsumer typically does not know which country or jurisdiction stores their data. Data centres are geographically dispersed — different legal frameworks may apply, creating conflicts over which laws govern the data.
4Data segregationCloud data sits in a shared environment alongside other customers' data. Encryption is necessary but not sufficient — data must be decrypted for processing, exposing it. Ask: how is data segregated at rest? Who designed and tested the encryption scheme?
5RecoveryWhat happens to data/services after a disaster or outage? Provider must disclose recovery procedures. Two key metrics: RPO (Recovery Point Objective — maximum data loss tolerated) and RTO (Recovery Time Objective — time allowed for recovery before business is impacted). Achieved via replication/redundancy.
6Investigative supportForensic investigation of illegal or inappropriate activity may be impossible because the consumer has little monitoring control over cloud infrastructure. Post-mortem analysis is hampered by limited visibility.
7Long-term viability (vendor lock-in)Consumer's workflows become dependent on one provider's proprietary APIs/formats. Switching triggers: price increase, provider bankruptcy, service shutdown, quality degradation, business dispute. Ask: how do I get data back? In what format? Can another application import it?
4 · Virtualization (Hypervisor) Threats
Virtualization is the key enabling technology of cloud. If the VMM/hypervisor is compromised, all VMs it hosts are in danger.
Full virtualization
ArchitectureVMs run on hypervisor which interacts directly with hardware
IsolationStrong — VMs do not touch host OS
Para-virtualization
ArchitectureVM interacts with host OS directly (penetrates one level higher)
IsolationWeaker — host OS is part of the attack surface

Hypervisor-specific threats

Clipboard / keylogging
Cross-VM data leakage
Some hypervisor technologies enable shared clipboard and key-stroke logging across virtual terminals. A malicious VM can capture inputs or inject data into another VM's session.
Rogue hypervisor / rootkit
Hypervisor-level rootkit
Attacker inserts a rogue hypervisor below the legitimate one; hides itself from normal malware detection; creates covert channels to dump unauthorized code or data.
VM escape
Break out of VM boundary
Exploit improper VM configuration to escape the guest VM and access the host OS or other VMs. Allows an attacker to cross the isolation boundary the hypervisor is supposed to enforce.
External modification
Unauthorized hypervisor changes
External modification of the hypervisor configuration or code, potentially through admin interface vulnerabilities. Result: loss of confidentiality, integrity, or availability for all hosted VMs.
5 · Access Control, Application & Data Lifecycle Threats

Access control & identity management

Access control
Role-based, MAC/DAC
Same as traditional systems but must address CIA in a shared-infrastructure context. Prevent identity theft through data mining on cloud-scale datasets — attacker can correlate behavioral patterns to infer identity.
Identity management
Authenticate users & services
Authenticate based on credentials and characteristics. Especially challenging in distributed/multi-provider settings where no single authority controls identity across the entire ecosystem.

Application-level attacks (cloud apps are mostly web-based)

SQL / command injection XML signature element wrapping Cross-site scripting (XSS) Flooding / DoS DNS poisoning Phishing WSDL metadata spoofing

Data lifecycle challenges

Confidentiality
Will provider peek at data?
Fear of loss of control — consumer must trust the provider not to access, share, or monetize their data. Encryption protects data in transit but data must be decrypted for processing, creating a window of exposure.
Integrity
Are computations correct?
How does the consumer verify that the provider executed computations faithfully and stored data without tampering? No mechanism in standard SLAs directly addresses computational integrity.
Availability
What if provider is DoS'd?
A DoS attack on the cloud provider brings down all its customers simultaneously. If the provider goes out of business, what happens to data and running processes?
Data location
Where are copies stored?
All copies and backups must reside only at locations allowed by contract, SLA, or regulation — but consumer cannot verify this without audit access. Archive latency and jurisdiction conflicts remain open problems.
6 · Inter-Cloud Communication Risks
Cascading access control violation: Cloud A → Cloud B → Cloud C communication chains can violate access control — a request may traverse providers and return to Cloud A with access to data the originating consumer should not have. Each cloud hop introduces a new access control boundary that may not be correctly enforced.
Provider-as-consumer: A cloud provider can itself be a consumer of another provider's services. This chain of trust makes end-to-end security analysis extremely complex.
Summary
Three cloud-unique threats: Co-tenancy (attacker can legitimately share your machine), lack of control (data/processes on provider premises), reputation fate sharing (shared IP consequences).
Gartner's 7 risks: Privileged user access · Regulatory compliance · Data location · Data segregation · Recovery (RPO/RTO) · Investigative support · Long-term viability (vendor lock-in). Memorize all seven.
RPO vs RTO: RPO = max data loss tolerated (how old can the recovery point be?). RTO = time allowed to restore service (how long can the system be down?). Both are contractual SLA parameters.
Hypervisor = single point of failure: If the VMM is compromised, all hosted VMs are compromised. Rogue hypervisors, VM escape, and keystroke logging are the primary vectors. Full virtualization provides stronger isolation than para-virtualization.
