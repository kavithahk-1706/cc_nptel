Lecture 51 MED priority

Dew Computing

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Introduces Dew Computing — a computing paradigm that brings cloud-level services down to the end device, enabling operation even without internet connectivity. Covers the two key features (independence and collaboration), the Dew Virtual Machine (DVM) architecture, six service models (WID, SID, DID, IAD, PID, Software in Dew), and open challenges. A distinct exam topic requiring definition recall and comparison with cloud/fog/edge.

1 · What is Dew Computing?
Dew Computing: A computing paradigm that combines the core concepts of cloud computing with the capabilities of end devices (PCs, smartphones, etc.) to provide services even when internet connectivity is unavailable. When connectivity is restored, the local state synchronizes with the cloud backend.
Name analogy: Cloud computing is remote (far above). Fog/Edge computing is closer to the ground. Dew is at ground level — at the device itself. Just as dew forms on surfaces at ground level, dew computing operates at the user's own device.
Canonical example — Dropbox: Your Dropbox folder is accessible even without internet (independence). When connectivity returns, changes sync automatically with the cloud (collaboration). This is the dew computing model.

Two Key Features

Feature 1
Independence
The local device must be able to provide services without a continuous internet connection. The user can read, write, and work on local data even when the cloud is unreachable. Independence is achieved through a local replica of the data/service.
Feature 2
Collaboration
The local dew service must be able to connect to the cloud and synchronize data when connectivity is available. Synchronization happens automatically (in an "automated mode") — the user does not need to manually trigger a sync in normal operation.
Key distinction from pure cloud computing: Cloud computing requires constant, reliable internet connectivity. Dew computing works without it — connectivity is needed only for synchronization, not for core service operation.
2 · Dew in the Computing Hierarchy
Smart IoT Modules / Smart Devices Lowest level — sensors, actuators, wearables. Dew computing is realizable here: devices work offline on last-synced data, sync with higher layers when connectivity is available.
Edge Devices Smartphones, tablets, laptops — the primary dew computing hosts. The Dew Virtual Machine (DVM) runs here, providing local services and managing cloud sync.
Fog / Edge Servers Intermediate servers closer to the user than the cloud. Fog computing is at this layer.
Cloud Server The remote, centralized backend. Dew devices sync with cloud when connectivity is available — but are not dependent on it for moment-to-moment operation.
Key insight: Dew computing does not rely on centralized cloud data centers for its moment-to-moment operation. It is a microservice-based paradigm that does not depend on centralized control — the DVM provides services locally and synchronizes when appropriate.
3 · Dew Architecture — The Dew Virtual Machine (DVM)
Dew Virtual Machine (DVM): An isolated, independent environment installed on the local system that runs the Dew Server. Analogous to installing Dropbox on your computer — the DVM is what you install to enable dew computing for a service. Has the capability of syncing with the cloud when connectivity is present.
DVM component
Dew Server
The core of the DVM. Serves user requests through the client services module. Performs synchronization between local data and remote cloud data. Pursues three goals: data replication, data distribution, and data synchronization. Also handles housekeeping (data organization in the dew database).
DVM component
Dew Client Program
Interacts with the end user (client) on the local device. The user-facing interface that requests services from the Dew Server. Decoupled from the server so the user experience remains smooth regardless of sync state.
DVM component
Dew DBMS
The local database management system within the DVM. Stores dew data in an organized way on the local device. Managed by the Dew Server for replication, distribution, and synchronization with the cloud database.
DVM component
Dew Client Services
The module that provides actual services to the end user — storage, web access, database queries, etc. Interfaces between the Dew Client Program and the Dew Server. May incorporate AI/intelligent modules for access prediction and caching decisions.
4 · Dew Service Models
ModelAcronymDescriptionExample
Infrastructure as DewIADLocal device is dynamically supported by cloud services. Local device may have an exact DVM clone running in the cloud (always kept in sync). Alternatively, all settings/data saved in cloud and pulled as needed.iCloud, system restore from cloud backup
Platform in DewPIDSoftware development suite installed on local device; settings, application data, deployment data, and online backups synchronized to cloud. Must be able to sync development data and system deployment data.GitHub (local repository + remote cloud sync)
Software in DewSIDConfiguration and ownership of software saved in cloud. Applications installed by user are tied to their account — can be reinstalled on any linked device without repurchase.Apple App Store, Google Play Store
Storage in DewSIDStorage of local device is partially or fully copied to cloud. User can access files anytime without constant connectivity (independence); folder contents automatically sync with cloud when connected (collaboration).Dropbox, Google Drive
Web in DewWIDLocal device possesses a duplicate fraction of the World Wide Web (or a modified/cached copy). Satisfies the independence feature — user can access web content offline. Synchronizes with live web to satisfy collaboration feature.Cached web pages, offline browser modes
Database in DewDIDBoth local device and cloud store copies of the same database. One is designated the primary (authoritative) version (the database administrator copy). Provides reliability — one can act as backup for the other.Offline-capable mobile apps with local DB sync
5 · Challenges in Dew Computing
Challenge
Power Management
The DVM runs on the local device alongside other services, drawing power. Deciding when to sync, how much background processing to do, and managing battery life — especially on mobile/IoT devices — is a significant challenge.
Challenge
Processor Utilization
The local processor must handle dew services alongside the device's normal workload. Efficient scheduling and resource sharing is required to avoid degrading the primary device experience.
Challenge
Data Storage
How much data to keep locally? Depends on cloud subscription AND local device capacity. Particularly challenging on low-resource devices (smartwatches, small IoT devices) where storage is severely constrained.
Challenge
OS Viability
The DVM must be compatible with the host device's operating system. Not all OS variants or device types may support a standard DVM implementation — portability across diverse device types is non-trivial.
Challenge
Programming Principles
What types of services can be provided? How configurable are the dew microservices? Defining programming models and APIs that work across the heterogeneous device landscape is an open research challenge.
Challenge
Security
Data stored locally in the dew system is exposed to the local environment and other services running on the device. Ensuring that dew data is not accessible to unauthorized services — and securing the sync channel — is a serious concern.
Summary
Dew Computing: A paradigm that brings cloud services to the end device level — users get service even without internet. Works on last-synced data offline; auto-syncs with cloud when connectivity returns.
Two defining features: Independence (device serves users without continuous internet) and Collaboration (device syncs with cloud when connected). Both must be present for a system to qualify as dew computing.
Name hierarchy: Cloud (remote, above) → Fog (intermediate) → Dew (ground level, at the device). Dropbox is the canonical example of a dew computing service.
Dew Virtual Machine (DVM): An isolated environment on the local device housing the Dew Server (sync + serve), Dew Client Program (user interface), Dew DBMS (local data storage), and Dew Client Services (service delivery layer).
Six service models: IAD (Infrastructure), PID (Platform), Software in Dew, Storage in Dew, Web in Dew (WID), Database in Dew (DID) — analogous to cloud IaaS/PaaS/SaaS but with local-offline capability.
Challenges: Power management, processor utilization, local storage constraints, OS viability across device types, programming model design, and security of locally-stored dew data.
