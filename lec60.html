Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Continuation of the IoHT case study — simulation results comparing cloud-only vs. fog-edge-cloud, hardware implementation details (custom body sensor, Raspberry Pi fog node, AWS cloud), activity detection using accelerometer, heart-attack alarm module, and DEW computing for offline resilience. Closes with a summary of the full 60-lecture course. Final lecture.

1 · Simulation Results — iFogSim Performance Evaluation
Simulation setup: Two configurations tested — Cloud-only (all modules in cloud) vs. Cloud-Fog-Edge (distributed modules). Varied number of users (4, 8, …) and number of area gateways across five configurations. Evaluated: average latency, network usage (kbps), cost of execution, energy consumption.

Key simulation finding: Fog-edge-cloud architecture consistently outperforms cloud-only on latency, network usage, execution cost, and cloud energy — at the cost of more complex local infrastructure setup and orchestration.
Cloud-only's advantage: Simple management — all infrastructure responsibility lies with the cloud provider. The organization does not need to own, configure, or maintain fog/edge nodes. For organizations without surplus on-premise resources, cloud-only may be the practical choice despite higher latency and cost.
2 · Hardware Implementation
Sensor Layer (IoT)
Custom Body Sensor Band
Customized band with BP sensor (diastolic + systolic), pulse sensor, and accelerometer (3-axis: x, y, z). Data transmitted via Wi-Fi or Bluetooth to mobile device. Custom hardware chosen to allow raw data extraction — commercial health bands restrict data access and customization.
Sensor Layer (IoT)
Node MCU Module Board
Low-cost microcontroller board (Node MCU / ESP8266) used alongside sensors for data acquisition and wireless transmission. Connects to mobile via Wi-Fi/Bluetooth.
Fog Layer
Raspberry Pi as Fog Node
Raspberry Pi used as the intermediate fog device — collects data from mobile edge, runs data filtering and processing modules locally before pushing to cloud. Acts as area gateway for the health monitoring pipeline.
Cloud Layer
AWS + IIT KGP Megamala
Amazon Web Services (public cloud) used for external cloud testing. IIT Kharagpur's in-house Megamala private cloud also tested. Both used to show end-to-end IoT-to-cloud realization. AWS preferred for richer managed services (no need to implement service-level procedures from scratch).
3 · Activity Detection and Heart Attack Alarm
Disclaimer: The following algorithms are for demonstration purposes only. They have no medical or clinical implication, have not been clinically tested, and should not be used for actual health decisions.

Activity Detection via Accelerometer

Step 1
Data Extraction
Accelerometer produces 3-axis readings (x, y, z). Resultant magnitude computed: √(x² + y² + z²). This single value captures overall movement intensity regardless of device orientation.
Step 2
5-Point Smoothing
Noise reduction: each smoothed signal value = average of (signal[t-2] + signal[t-1] + signal[t] + signal[t+1] + signal[t+2]). Reduces transient noise from sensor jitter while preserving actual activity patterns.
Step 3
Feature Extraction
From filtered signal: minimum amplitude, mean amplitude, standard deviation, energy in time domain, energy in frequency domain. These features capture the statistical signature of different activity types.
Step 4
K-Nearest Neighbor Classification
kNN classifier trained on extracted features to classify activity type (walking, sitting, running, falling, etc.). Alternative classifiers (SVM, neural networks) can be used if the fog/edge hardware supports them.

Heart Attack Alarm (Demonstration)

Simple threshold rule: If diastolic BP > 170 AND systolic BP ≥ 180 → alarm = TRUE → alert displayed on mobile. Otherwise alarm = FALSE. This is a simple if-then rule, not a clinical diagnostic — actual heart attack prediction requires validated clinical algorithms and domain expert involvement.
4 · DEW Computing — Resilience Against Connectivity Loss
DEW (Dew) Computing: An on-premise computing paradigm where local computers provide functionality independent of cloud services while also being collaborative with the cloud when connected. Think of it like Dropbox — you work locally even when offline; the system syncs with the cloud when connectivity is restored.
Why DEW matters for IoHT: If the network connection to the cloud/fog is lost, health monitoring should not fail. DEW server provides a local fallback — continues processing and storing data on-premise. When connectivity returns, data syncs with cloud. Result: system remains functional even during network outages.
Assumption: DEW works best when connectivity outages are short — the DEW server can handle the interim load until the connection restores. If outages are prolonged and data is mutable/high-volume, DEW faces challenges in keeping up with full cloud capabilities.

6 · Course Conclusion
What this course covered (end-to-end): Started with cloud computing basics (subscription model, SLA, economics, CV and utility pricing) → cloud architecture (IaaS/PaaS/SaaS) + deployment models → distributed programming models (MapReduce, Spark) → cloud storage and databases → resource management and scheduling → containers and microservices → cloud security → fog, edge, and IoT → sustainable computing → 5G, CPS, and emerging paradigms → case studies (spatial cloud, IoHT).
The paradigm is here: Cloud-fog-edge-IoT is no longer experimental — it is the de facto computing paradigm for large-scale, distributed, resource-constrained environments. Understanding when to use cloud-only vs. hybrid architectures, how to optimize across layers, and how to build SLA-aware systems is the core competency this course targets.
Summary
Fog-edge-cloud results: Consistently lower latency, network usage, execution cost, and cloud energy than cloud-only. Trade-off: more complex on-premise infrastructure. Use fog/edge when surplus on-premise resources exist and real-time response is required.
Activity detection pipeline: 3-axis accelerometer → √(x²+y²+z²) magnitude → 5-point smoothing → feature extraction (mean, std, energy) → kNN classifier. Fog node processes this pipeline locally for near-real-time response.
DEW computing: On-premise server that operates independently of cloud when offline and syncs when connected. Adds resilience to the fog-edge-cloud continuum — critical for health applications where connectivity disruptions must not cause system failure.
Cloud-to-things continuum: The dominant modern computing paradigm. Not a disjoint set of layers — a hierarchically orchestrated, integrated system where the right computation happens at the right level for optimal latency, cost, bandwidth, and resilience.
