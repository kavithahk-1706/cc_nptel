Lecture 31 MED priority

Mobile Cloud Computing – I

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Introduces mobile cloud computing (MCC): the motivation for offloading computation from resource-constrained mobile devices to the cloud, the MBaaS paradigm, system architecture with profiler/solver/synchronizer components, key advantages, and open challenges. Survey-level lecture; good for short-answer exam questions on MCC definition, runtime offloading issues, and challenge areas.

1 · What is Mobile Cloud Computing (MCC)
Definition: MCC is a combination of cloud computing, mobile computing, and wireless networks that brings rich computational resources to mobile users — providing data storage and processing services on the cloud while moving computing power and data storage away from the mobile device.

Three perspectives

Combination
Cloud + mobile + wireless networks to deliver compute benefits to mobile users, network operators, and cloud providers — a "win" for all parties.
Offloading
Mobile devices offload resource-hungry computation modules to the cloud and retrieve results — the device handles sensing and lightweight processing only.
Migration
Computing power and data storage are migrated to cloud infrastructure, freeing the mobile device from both processing and storage burden.

Motivation

Enablers
Growth drivers
Huge proliferation of smartphones; increased device capability; easy, low-cost high-bandwidth internet access from mobile devices.
Constraints
Resource challenges
Battery life, limited storage, constrained bandwidth. Resource-hungry applications cannot run sustainably on the device alone.
Cloud side
Cloud advantage
Low-cost, elastic, on-demand resources on a pay-as-you-go model. Cloud can provide virtually unlimited compute and storage.
Use case
Example
Mobile device senses environmental data and performs initial analysis; predictive modelling (resource-hungry) is offloaded to the cloud; results returned to device for decision-making.
2 · Mobile Backend as a Service (MBaaS)
MBaaS: A model that gives mobile application developers a way to connect their apps to cloud storage and processing, abstracting away the complexity of managing back-end infrastructure so developers can focus on front-end development.
Multiple apps on shared backend Multiple developer teams Multiple mobile platforms Third-party API integration Enterprise connectivity

Real-world examples of cloud-augmented mobile

Amazon Silk (split browser) Apple Siri Apple iCloud Image recognition apps Augmented reality apps
Common pattern: All these examples rely on a high-bandwidth wireless backbone to make the cloud appear seamlessly integrated — the processing on the cloud feels as if it runs on the device itself.
3 · Runtime Offloading — Challenges
Dynamic offloading is extremely non-trivial. Doing anything at runtime is fundamentally more complex than static partitioning.

Key runtime offloading issues

IssueDescription
Dynamic application profilingContinuously monitoring the app's execution to determine which modules are resource-intensive
Runtime application partitioningDividing the app into device-side and cloud-side components at run time
Migration of intensive componentsMoving computationally heavy modules to cloud while maintaining correctness
Continuous synchronizationKeeping device and cloud execution states consistent throughout the entire runtime

Key system components

Profiler
Monitors application execution to collect data on execution time, power consumption, and network traffic. Determines what to offload.
Solver
Decides which parts of the app run on device and which are uploaded to the cloud. Central decision-maker for partitioning.
Synchronizer
Collects results of split execution, combines them, and makes the execution transparent to the user — feels like the app ran locally end-to-end.
Transparency requirement: After partitioned execution, the synchronizer must stitch results so the user perceives zero interruption — achieving this seamlessly is one of the hardest problems in MCC.
4 · MCC System Architecture
Cloud Cloud controllers process requests; cloud data sender + server nodes; SLA-bound execution queues; Application Service Provider
Wireless Network Internet + mobile network (ISP + Network Operators); handles latency — critical bottleneck
Mobile Devices (SMD) Profiler → Solver → SMD Synchronizer → Workload Manager; connected to base station
Flow: Mobile device connects to base station → subscriber request transmitted via internet → cloud controller processes request → response returned to mobile user. Network latency is the critical non-compute bottleneck.
5 · Advantages of MCC
Energy
Extended battery life
Offloading resource-hungry computation reduces on-device CPU usage → less power draw → longer battery life. Remote application execution saves energy significantly.
Storage
Improved data storage capacity
Data stored on the cloud (not device) — continuous data ingestion (e.g., environmental sensors) without filling local storage. Huge cloud capacity available.
Reliability
Better availability
Data loss on device (lost/broken phone) does not result in permanent data loss. Cloud's redundant storage keeps data safe. Services remain accessible while moving between devices.
Security
Comprehensive security model
Cloud can host virus scanning and malicious code detection services. DRM (digital rights management) for copyrighted content possible. Data + services are omnipresent — accessible from any device.
Provisioning
Dynamic scalability
Cloud elasticity allows dynamic provisioning and infinite scalability for mobile apps. Multi-tenancy shares resources across users and applications efficiently.
Integration
Ease of integration
Multiple services from different providers can be integrated through the cloud to meet user demands. Standardized API access simplifies cross-platform connectivity.
6 · Open Challenges in MCC
ChallengeDescription
Security & PrivacyTwo sub-categories: (1) security of mobile users (malicious code, GPS privacy, location-based service leakage); (2) security of cloud data. Multi-provider path means the user often doesn't know which cloud actually stores their data.
Context-aware servicesDifferent users have different needs (streaming, email, scientific computation). Services must adapt to local context: data type, network status, device environment, user preferences.
Network access managementImproving link performance while optimizing limited bandwidth. Latency is the primary bottleneck; multiple users share the same wireless and backbone resources.
QoS & PricingMultiple parties involved (cloud provider + mobile network operator). Business model and SLA structure must satisfy both provider economics and user expectations.
Standard interfacesNeed standard APIs across different devices and application types so MCC frameworks are interoperable and reusable.
Service convergenceServices differentiated by type, cost, availability, quality. Need a scheme for mobile users to utilize multiple clouds in a unified, seamless fashion.
Security complexity: The mobile user typically subscribes to a mobile service provider, not the cloud itself. The service framework may silently select different cloud providers based on availability and pricing — making security assurance very difficult to guarantee end-to-end.
Threat model (from lecture): Two approaches to mobile security — (1) host agent on the device inspects file activity locally; (2) smartphone records minimum execution trace and sends it to a remote security server on the cloud for analysis.
Summary
MCC Definition: Cloud + mobile + wireless — offloads resource-hungry computation from constrained mobile devices to elastic cloud infrastructure, returning only results.
Core benefit: Battery life extended, storage unlimited, reliability improved — all because the heavy lifting moves off-device.
MBaaS: Backend-as-a-Service for mobile developers; abstracts infrastructure management so focus stays on front-end app logic.
Runtime offloading caveat: Dynamic partitioning, migration, and synchronization at runtime are extremely non-trivial. Profiler + Solver + Synchronizer components are needed but making them transparent to users is an open research problem.
Security caveat: Mobile user often cannot know which cloud provider holds their data — multi-provider paths make end-to-end security guarantees difficult.
