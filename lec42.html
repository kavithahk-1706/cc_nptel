Lecture 42 HIGH priority

Resource Management — I

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Introduces resource management challenges in the cloud-fog-edge computing paradigm — why managing fog/edge resources is non-trivial, and a taxonomy of the three major components: architecture (data flow, control, tenancy), infrastructure (hardware, system software, middleware), and algorithms (discovery, benchmarking, load balancing, placement). Conceptually dense survey-level content; expect exam questions on the three-component taxonomy and algorithmic categories.

1 · Why Resource Management in the Cloud-Fog-Edge Paradigm?
Core problem: Adding fog and edge layers to the cloud does not automatically improve things. Resource management is non-trivial — some fog nodes may be over-constrained while others have spare capacity. Without explicit management, gains from the fog paradigm are not realized.
Problem
Heterogeneous Resources
Fog nodes vary greatly — routers, gateways, mobile devices, dedicated micro-data centers. Some are compute-constrained; others have spare capacity. Resource-aware allocation is required across all of them.
Problem
Cost of Management Itself
A fog resource manager consumes time and compute resources to perform management decisions. This overhead must be accounted for — management is not free.
Requirement
Resource Allocation
Given a pool of fog resources, how should they be distributed across tasks and users? Includes resource provisioning, task scheduling, and maintaining appropriate QoS levels.
Requirement
Workload Balancing
Load should be distributed as equitably as possible across fog nodes. Skewed load (all requests going to one fog node) degrades performance and wastes available resources elsewhere.
2 · Fog-Edge Layer — Key Roles

The fog layer sits between IoT/edge sensing devices and the cloud. It serves three operational roles depending on the application:

Aggregation
Collect readings from multiple sensors, combine them (e.g., room-level temperature from multiple sensors), and transmit only the aggregated result to the cloud — reducing upstream bandwidth.
Local Decision
Execute application logic entirely at the fog node without involving the cloud. Example: alarm trigger when temperature exceeds threshold — no cloud round-trip needed for a binary decision.
Delegation to Cloud
Forward requests to cloud when: (a) fog lacks compute capability for that analysis, or (b) the decision requires global context not available locally (e.g., institution-wide HVAC status).
Vehicular network example: Vehicles (edge) communicate via V2V or via roadside infrastructure (fog). License revocation or anomaly detection across many vehicles requires cloud-level global context. Local incidents (speed adjustment) are fog-level decisions made at roadside infrastructure.
Healthcare example: A body area network transmits health parameters to a nearby mobile device or local server acting as fog. Basic alerting (vital crossing threshold) happens at fog; longitudinal analysis and cross-patient comparison happen at cloud.
3 · Mobility Challenge

IoT and edge devices can be mobile. When a device moves from one fog node's coverage area to another, resource management must handle the transition.

Handoff problem: If a sensor session or data aggregation is in progress under fog node A and the device moves to fog node B's area, the state must be synchronized. Losing the partial aggregation wastes resources and may corrupt results.
Contrast: Temperature / humidity sensors in a building are static — no mobility concerns. Vehicular networks are highly mobile — handoffs happen continuously and state synchronization across fog nodes is critical.
4 · Resource Management Taxonomy

Resource management in cloud-fog-edge computing divides into three orthogonal components: Architecture, Infrastructure, and Algorithms.

Key insight: All three components interact — the architecture constrains what infrastructure is deployed, and both together determine which algorithms are feasible and necessary.
5 · Architecture — Data Flow, Control, Tenancy
Data Flow
Direction and shape of workload movement in the computing ecosystem. Workloads may flow: user → edge → fog → cloud, or cloud → edge (push model). Application requirements determine flow direction and intermediate processing points. Resource management must align with this flow.
Control
How resources are governed: centralized (single controller manages all fog nodes — suitable for small, static deployments), distributed (each fog node self-manages — suitable for vehicular or wide-area networks), or hierarchical (tiered control matching the fog-cloud hierarchy). Choice depends on geographic distribution and application dynamism.
Tenancy
What runs where and how many tenants share a resource. A fog node may host a single application or multiple applications simultaneously. Tenancy decisions determine resource partitioning, isolation guarantees, and interference between co-located workloads.
6 · Infrastructure — Hardware, System Software, Middleware
Hardware
Small form-factor devices repurposed or augmented for compute: network gateways, Wi-Fi routers, set-top boxes, small home servers, edge ISP servers, on-board vehicle units (OBUs), drones. Key difference from cloud: hardware is heterogeneous, resource-limited, and geographically dispersed.
System Software
Runs directly on fog/edge hardware (CPU, memory, devices). Manages resources and distributes them within the fog-edge tier — operating systems, virtualization software, hypervisors. Not application-specific; it is the platform on which applications run.
Middleware
Runs on top of the operating system; provides services not supported by system software. Coordinates distributed computing nodes; handles deployment of VMs and containers to edge nodes. Bridges the gap between system software and application logic across multiple nodes.
7 · Algorithms — Discovery, Benchmarking, Load Balancing, Placement
Algorithm CategoryPurposeKey Challenge
Discovery Identify available and free edge/fog resources where workloads can be deployed. Analogous to service discovery in distributed systems. Dynamic availability — fog nodes may join or leave; resources fluctuate with mobile devices.
Benchmarking Measure and characterize performance of computing resources (CPU speed, memory bandwidth, storage, networking throughput). Dictates overall system performance. Fog hardware is heterogeneous — benchmarks must generalize across different device types.
Load Balancing Distribute tasks across edge data centers and fog nodes using optimization or search-based techniques to prevent skewed load and underutilization. Geographically dispersed nodes; task arrival is dynamic; optimization problems may be NP-hard.
Placement Decide which fog or edge node hosts a given incoming compute task. Must consider available resources, current environment, and SLA constraints. Environment is dynamic (mobile devices, variable load); may require iterative or condition-aware techniques.
Note: These algorithmic challenges also appear in classical distributed computing. The cloud-fog-edge paradigm adds urgency via harder latency constraints and greater node heterogeneity.
Summary
Three-Component Taxonomy: Resource management in cloud-fog-edge decomposes into Architecture (data flow, control, tenancy), Infrastructure (hardware, system software, middleware), and Algorithms (discovery, benchmarking, load balancing, placement).
Management is not free: A fog resource manager itself consumes time and resources — the overhead must be factored into the net benefit analysis of deploying the fog paradigm.
Control options: Centralized control suits small static fog deployments; distributed control suits large-scale or highly mobile scenarios (vehicular networks); hierarchical control matches the natural cloud-fog-edge hierarchy.
Placement is the hardest problem: Deciding which fog node runs which task, under dynamic environmental conditions and resource constraints, is the central algorithmic challenge in fog-edge resource management.
