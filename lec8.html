Lecture 08 High priority

XML Basics

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Introduces XML as the basic building block of service oriented architecture and web services, which is how heterogeneous cloud services interoperate. Covers XML structure, the tree data model, parsers, well-formed versus valid documents, DTDs, entities, and XML Schema. Moderately technical and foundational for the SOA and SaaS lectures that follow.

1 · Why XML for Cloud
Cloud offers many services (XaaS), so a protocol is needed that lets them interoperate. For the consumer it is independent of how and where the provider hosts the cloud, and of how the client accesses it. This is a service oriented architecture: web services let loosely coupled, heterogeneous services interoperate to achieve an expected output.
Key insight: one of the basic building blocks of all such service exchanges is XML. In SOA there are three major components (consumer, provider and registry), and the messages between them (SOAP, WSDL, UDDI) are all XML documents.
The term "XML" has evolved to imply a growing family of software tools and standards: how XML data is represented and processed, and application frameworks (tools, dialects) based on XML. Most popular XML discussion refers to this latter meaning; both are covered.
2 · What is XML?
XML (Extensible Markup Language) is a syntax for encoding text-based data (words, phrases, numbers). Unlike HTML, which is a data display language, XML is more of a data transformation language that helps achieve interoperation.
Text-based syntax
Written using printable Unicode characters; no explicit binary data and no character encoding issues.
Extensible
You define your own elements (essentially data types) within the constraints of the syntax rules.
Universal format
Syntax rules ensure all XML processing software must handle a given piece of XML data identically.
Guiding principle: if you can read and process it, so can anybody else. This is what makes XML ubiquitous.

Since tags are user defined, the meaning of a tag must be identifiable. Example: a tag called "table" could belong to the furniture category or to the word processing category. The XML namespace lets us define our own user defined elements so the other end knows which one is meant.

4 · XML: Why It Is This Way
simple
Simple, like HTML, but not quite so simple
Strict syntax rules eliminate syntax errors. The syntax defines structure (hierarchically) and names the structural parts (element names), so XML is self-describing data.
extensible
Extensible, unlike HTML
Vocabulary is not fixed; you can create your own language of tags and elements. Strict syntax ensures such markup can still be reliably processed.
distributed
Designed for a distributed environment
Data can be all over the place and can be retrieved and used reliably, interoperating with different nodes of a distributed system.
mixing
Can mix different data types
One set of tags can be mixed with another, and the resulting data can still be reliably processed.
Example: an institute combines student academic data (from the academic section) with student activity data (from another centre) to find the best all-rounder of a semester, batch or year. Distributed, diverse data sets are mixed on the fly into a new data set.

The parser must verify that the XML data is syntactically correct. Such data is said to be well-formed, the minimal requirement to "be" XML. A parser must stop processing if the data is not well-formed, i.e. stop and throw an exception to the XML-based application. The XML 1.0 spec requires this behaviour.
6 · DTD and Internal Entities
Like a relational database needs a table schema, user defined hierarchical XML needs a definition of which elements exist, their levels and their types. Earlier this was done with the DTD (Document Type Declaration). First the document type is declared, and the rest of the data follows it.
▶ 14:40
Worth watching: a DOCTYPE with an internal entity declaration (messageHeader) and its entity reference used inside the transfers element.
Well-formed XML
MeaningSyntactically correct
MinimumThe minimum requirement to be XML and be processable
Valid XML
MeaningWell-formed and also consistent with the specific DTD or XSD (schema)
RelationAll valid XML documents are well-formed
While getting XML data, the parser consults the DTD. Many parsers can operate in either validating or non-validating mode (parameter dependent); the relationship and behaviour depend on parser nature.

How the parser handles internal entities

The parser processes the DTD content, identifies the internal entities and checks that each entity is well-formed. There are explicit syntax rules for DTD content, and well-formed XML must be correct there too. It then replaces every occurrence of an entity reference by the referenced entity, doing so recursively within entities. The resolved data object is then made available to the XML application. By then, well-formedness checking and DTD checking (validation) are done.
7 · External Entities and Types of Parsers
▶ 18:45
Worth watching: an external entity declaration pointing to a file via a URL, so the entity can be shared by multiple resources.
An external entity is put in another file and referred to by a URL, so it can be shared by multiple resources. With internal entities the DTD or schema is defined in the document itself; with external ones it refers to an external structure. The parser processes the DTD content, identifies the external entities, tries to resolve them, and replaces each entity reference recursively as with internal entities.
Problem: what if the parser cannot find the external entity (e.g. due to firewall blockage)? That depends on the application and parser type.
Validating parser
EntitiesMust retrieve all entities and process all DTD content
On failureStops processing and indicates a failure
AlsoTests compatibility with the DTD rules (allowed elements, attributes etc.)
Non-validating parser
EntitiesTries to retrieve all entities defined in the DTD
On failureCeases processing the DTD content at the first entity it cannot find; this is not an error
OutputMakes the XML data and the names of unresolved entities available to the application
Key insight: application behaviour depends on the parser type.
8 · Special Issues: Characters and Charsets
The XML specification defines what characters can be used as whitespace in tags.
The EBCDIC character NEL cannot be used as whitespace Characters not in the encoding charset (e.g. Greek characters in an ISO-Latin-1 document) use character references Binary data must be encoded as printable characters
Example: the character reference &#9824; stands for the 9824th character of the Unicode character set, the spades character.
9 · DTD vs XML Schema
There are two ways to define the structure of an XML document: the DTD (part of the core XML spec) and XML Schema (XSD), a newer specification (2001) that allows stronger constraints on XML documents. Both do broadly the same job.
DTD
SyntaxNot written as an XML document
PowerLess powerful
XML Schema (XSD)
SyntaxWritten in XML, so schema handling goes hand in hand with XML data
PowerMuch more powerful: used for type validation and for relating database schemas to XML models
A DTD or schema specifies allowed elements and attribute data, hierarchical nesting rules, and element content and type restrictions. It does not contain any XML data; the information is in the XML file and only the structure is defined in the schema.
Why it matters for interoperation: two organizations only need to agree on the structure of the exchange, not exchange data. Sharing data raises privacy issues and maintenance costs, while sharing the schema is not critical. Using a schema, one can also create a database table and transfer data between the two parties. Today schemas are primarily used for interoperation between parties.
Example: IIT Kharagpur and a bank (State Bank, Punjab Bank etc.) doing payment transfers must first agree on the structure of student data. IIT Kharagpur only tells the bank what its student schema is like, not how many students there are or their properties.
10 · DTD Examples and Use in Interoperation
▶ 29:20
Worth watching: an internal DTD with element and attribute declarations for transfers, fundsTransfer, from, to and amount.
An example DTD can be part of the document itself. A DTD does not follow the XML document format, whereas a schema is itself represented as an XML document.
External DTD: the DOCTYPE refers to a DTD file by a URL (SYSTEM identifier); the DTD file must be there and accessible. When consuming data from another provider, the external DTD shows what sort of data is coming, e.g. its ordering and hierarchy.
Use in practice: the parser filters and extracts the portion of data needed, and transformations such as centigrade to fahrenheit or meter to feet can be done at the consumer's end before passing the data to the application. This is useful for interoperation and for realizing cloud, especially SaaS models, to be continued in later lectures.
Summary
XML in cloud: a basic building block of service oriented architecture; SOAP, WSDL and UDDI are XML documents that let heterogeneous services interoperate.
XML vs HTML: XML is text-based, extensible (user defined tags), universal and self-describing, and is a data transformation language, while HTML has predefined tags for display.
Structure: a hierarchical tree of elements and attributes, with a declaration and namespaces to disambiguate user defined tags.
Parser: verifies syntax and must stop and throw an exception if the data is not well-formed; well-formed is the minimum requirement for XML.
Well-formed vs valid: valid means well-formed and conforming to its DTD or schema; all valid documents are well-formed.
Entities: the parser resolves internal and external entity references recursively before passing data to the application.
Parser types: a validating parser must retrieve all entities and fails if it cannot, while a non-validating parser stops processing the DTD at the first unresolved entity without error; application behaviour depends on parser type.
DTD vs XSD: XSD (2001) is written in XML and is much more powerful; neither contains data, only structure.
Example: IIT Kharagpur and a bank agree on the student data schema without exchanging any student data.
