Cloud Security III — Case Study: Co-Residence Attacks on EC2

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Applied case study based on the ACM CCS 2009 paper "Hey, You, Get Off of My Cloud." Covers co-residence attacks on Amazon EC2: cloud cartography, instance placement exploits, co-residency detection, cross-VM side-channel attacks, and countermeasures. Reinforces cloud-specific security risks from lec27 with concrete experimental evidence.

1 · The Paper — Context & Key Claim
"Hey, You, Get Off of My Cloud: Exploring Information Leakage in Third-Party Compute Clouds" — ACM CCS 2009. Claimed as first work in cloud cartography. Experiments conducted on Amazon EC2.
Key result: 40% success rate in achieving co-residence with the target VM on a real commercial cloud (Amazon EC2) — without any insider access or provider cooperation.
Objective of this lecture: Not to expose EC2 vulnerabilities, but to understand what types of cloud-specific security risks are practically exploitable. The paper uses EC2 as a real-world test bed.
2 · New Risk Factors in Cloud
Trust & dependency
Customer must trust the provider
Customer delegates data, processes, and applications to the cloud provider's infrastructure. They must trust that the provider preserves the privacy of data and the integrity of all computations — with no independent means of verification.
Multi-tenancy
Co-location with unknown parties
Multiple customers' VMs share the same physical server. The customer has no control over who they share physical hardware with. A malicious co-tenant can potentially exploit shared physical resources to extract information.

Multi-tenancy threat vectors

Side-channel / cross-VM information leakage via shared physical resources Potential extraction of RSA and AES secret keys via side channels Vulnerable VM isolation (hypervisor escape) No control over which other tenants share the same server
3 · The Attack Model — Two Steps
Step 1: Placement
GoalPlace attacker's VM on the same physical server as the target VM
ChallengeProvider does not disclose where VMs are placed; co-location is opaque
MethodCloud cartography + instance placement locality exploitation
Step 2: Extraction
GoalExtract confidential information from the victim VM via side channels
VectorsKeystroke timing, cache usage patterns, covert channels, traffic rate analysis
AdvantageOnce co-resident, attacker has direct access to shared physical resources
Threat model assumptions: Provider and infrastructure are trusted (no insider attack). Adversaries are non-provider-affiliated customers — they interact as ordinary users. Victims run services requiring privacy/confidentiality.
4 · Amazon EC2 Architecture (as studied)
Instance parameters
Three degrees of freedom
Instance type (m1.small, m1.medium, m1.large, m1.xlarge), Region (US, EU, Asia), Availability Zone (within a region, e.g. US-East, US-West). Customers are randomly assigned to a physical machine based on these three choices.
Hypervisor
Xen + Dom0
Dom0 is the privileged VM that manages guest images, provisions physical resources, controls access rights, and routes packets. Dom0 reports itself as a hop in traceroute. An instance is assigned to a single physical machine for its entire lifetime.
Addressing
Internal + External IP
Each instance gets an internal IP (used within the cloud) and an external IP (used outside the cloud). Within the cloud, both DNS names resolve to the internal IP. Outside the cloud, the external DNS name resolves to the external IP.
Availability zones
Physically separate power & network
Each AZ has separate power and network infrastructure. Different IP blocks are used per AZ. A power failure or network issue in one AZ does not cascade to others — this isolation is also what makes placement cartography possible (AZ → IP block correlation).
5 · Step 1a — Cloud Cartography (Finding the Target)
Cloud cartography: Building a map of which IP address ranges correspond to which instance types and availability zones, so an attacker can choose parameters that place their VM near the target.

Probing methodology

External probe
From outside EC2 → EC2 instance
Used tools: nmap, hping, wget. Scanned ports 80 (HTTP) and 443 (HTTPS) across known EC2 IP prefixes to find responsive IPs. Then used DNS lookups to map each public IP to its internal EC2 address. Result: ~14,000 unique internal IPs discovered.
Internal probe
From EC2 instance → EC2 instance
Originates from an attacker-controlled EC2 instance with an EC2 target as destination. Allows direct internal IP probing, round-trip time measurement, and traceroute to identify Dom0 hops — all from inside the cloud network.
Key observation: Different availability zones and instance types correspond to disjoint IP address blocks. By launching probe instances and observing which /24 prefixes they land in, an attacker can reverse-engineer the placement partitioning scheme.
6 · Step 1b — Co-Residency Detection
Co-residency check: Two instances are likely co-resident if they share the same Dom0 IP, have small round-trip times, and have numerically close internal IP addresses (typically within a /24).

Detection method (non-invasive)

  1. Compare internal IP addresses — are they in the same or adjacent /24 block?
  2. Perform TCP SYN traceroute to an open port on the target — if only one hop (the Dom0), they are on the same physical server.
  3. Check requires at most two TCP SYN packets — no full TCP connection is established; victim is unaware.
Disk-based covert channels can also be used to confirm co-residency: if two instances under attacker control can communicate via a shared covert channel, they are confirmed co-resident.
7 · Step 1c — Causing Co-Residency
Brute force placement
Launch many probe instances
Launch numerous instances in the target's availability zone and instance type. With enough attempts, probability of landing on the same physical server increases — 40% success rate reported in the paper.
Temporal locality
Target recently-launched instances
EC2 tends to assign freshly launched instances to a small set of machines. Launching attacker instances at the same time as (or just after) the victim increases co-location probability. Parallel placement locality: two instances launched at roughly the same time are often assigned to the same machine.
Placement locality types: Sequential locality — IP addresses repeat when new instances are launched after terminating old ones from the same account. Parallel locality — instances launched simultaneously from different accounts tend toward the same physical server. Instance flooding — launching many parallel instances in the same AZ/type maximizes coverage.
8 · Step 2 — Exploiting Co-Residency (Side-Channel Attacks)
Keystroke timing
Password inference
SSH keystrokes generate detectable inter-packet timing patterns across the shared network stack. A co-resident attacker monitoring these timings can statistically narrow down the password being typed.
Cache usage analysis
Process activity inference
Monitor patterns of CPU cache evictions. The cache usage pattern of a co-resident process leaks information about what the process is doing — allows classification of workload type or detection of sensitive operations.
Covert channels
Intentional data leakage
Create a covert communication path between two attacker-controlled co-resident VMs via shared resources (disk I/O, network timing, CPU load). Bypasses any network-layer security controls — channel exists entirely within the physical server.
Traffic rate estimation
Victim activity profiling
Measure victim's HTTP traffic rates from a co-resident vantage point. Distinguish no-traffic, idle HTTP, and active HTTP states — useful for timing attacks or profiling customer behavior patterns.

9 · Countermeasures & Their Limitations
CountermeasureHow it helpsLimitation
Randomized IP allocationBlocks cartography tools (nmap, traceroute) from mapping AZ→IP correspondenceRandomization conflicts with resource management and routing optimization; operationally expensive for the provider
Prevent Dom0 identificationStops co-residency check based on single-hop tracerouteAttacker can still use other heuristics (IP proximity, timing); doesn't eliminate co-residency
No co-location (strict isolation)Eliminates co-residency entirely — physically separate each tenantExtremely inefficient for the provider; defeats the economics of multi-tenant cloud; not commercially viable
Side-channel mitigationCache partitioning, noise injection, timing randomizationRemains an open research problem; each mitigation can often be bypassed; performance overhead is significant
Summary
Two-step attack: Placement (co-locate attacker VM with victim VM via cloud cartography + locality exploitation) followed by Extraction (side-channel attacks on shared physical resources).
40% co-residence success: Against a real commercial cloud (Amazon EC2) with no insider access — demonstrates that co-residence attacks are not theoretical; they are practically achievable.
Side-channel vectors: Keystroke timing (password inference), cache usage analysis (workload classification), covert channels (intentional data exfiltration between co-resident VMs), and traffic rate profiling.
No clean fix: All countermeasures carry significant operational or efficiency costs. Side-channel attacks on shared infrastructure remain an open and unsolved problem in cloud security.
