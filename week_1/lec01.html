Lecture 01 med priority

Cloud Computing — Overview

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

An introductory lecture that establishes the broad definition of computing, surveys the full course roadmap, and traces the evolution of computing paradigms — from centralised mainframes through distributed, grid, cluster, and utility computing — that set the stage for cloud. It closes with a detailed look at distributed computing: its definition, examples, node types, properties, and the motivations behind it. Mostly conceptual and definitional; very light on math or implementation detail.

1 · What is Computing

As defined by the ACM Computing Curricula (2005), computing refers to any goal-oriented activity that requires, benefits from, or creates computing machinery. This spans:

Hardware & software systems Intelligent systems / AI Communication systems Information gathering & processing

The definition is intentionally wide — it covers end users ranging from high-end researchers and professionals all the way to students and everyday citizens.

3 · Key Concepts Briefly Introduced

Service Level Agreement (SLA)

A formal agreement between a cloud service provider (CSP) and a consumer that specifies guaranteed minimum service levels. Key parameters include:

Availability (e.g. 99.9%) Downtime tolerance Quality of Service (QoS) Resource pooling commitments
Example: During an exam period, availability must be near 100% with redundant services; during a practice session, 90% may be acceptable. The SLA specifies this contractually, and the provider charges accordingly.

Cloudonomics

Analogy (from lecture): If you commute 220 km daily, buying a car is economical. If you commute 50–100 km once a month, hiring is better. Similarly, whether purchasing or renting cloud compute resources is cost-effective depends on your usage pattern. Cloud is not always the cheaper option.

Resource Management (Provider Side)

The CSP must manage CPU, RAM, disk storage, and network connectivity to avoid two failure modes:

Under-provisioning
ProblemCannot serve demand; SLA breached
AnalogyStationery shop runs out of notebooks before semester ends
Over-provisioning
ProblemResources idle; incurs unnecessary cost
AnalogyShop stocked so full that goods spill outside

Data Management

Data in cloud must be handled for storage, scalability, and service delivery. Conventional DBMS approaches may not scale. Example services like Dropbox illustrate storage-as-a-service.

Critical point: Unlike applications, data cannot be reinstalled. A lost report or dataset is permanently gone unless recovery mechanisms exist — making data security and backup a top concern.

Security

When your compute and storage live on someone else's infrastructure, three interlinked concerns arise — described as a triangle:

Trust
How much do you trust a given CSP over another? How is trustworthiness evaluated and quantified?
Reputation
A provider's track record of reliability, security, and SLA adherence factors into selection and risk modelling.
Risk
Risk of data loss, application failure, or loss of end-customers (who you are serving using that cloud).

Also relevant: identity & access management (IAM), role-based access control (RBAC), and infrastructure-level security.

4 · Evolution of Computing Paradigms

Cloud computing did not appear from nowhere — it is an evolution of several prior paradigms, each addressing different needs with their own trade-offs:

Cloud Computing on-demand, pay-per-use, internet-scale
Utility Computing computing as a metered utility service
Grid Computing federated resources across organisations
Cluster Computing tightly coupled nodes, high performance
Distributed Computing the foundational paradigm — "mother of all these"
Note: These paradigms did not arrive strictly sequentially — they represent different dimensions of computing need that co-evolved. Each has advantages and limitations; collectively they enabled cloud computing.

Centralised Computing (Predecessor)

Worth watching: Slide illustrating the mainframe/terminal architecture of centralised computing.

Before distributed systems, computing followed a centralised model: mainframe computers with multiple dumb terminals. Jobs were submitted to the mainframe, executed centrally, and results returned to the terminal. This is logically a uni-processor / single-processing-node model. Still used where centralised control is required.

5 · Distributed Computing
▶ 18:43
Worth watching: Slide with the formal definition of distributed systems.

Distributed computing is a field of computer science studying systems where multiple autonomous entities collaborate to solve computational problems. Two complementary definitions given:

Definition 1 (System view): A set of several autonomous computational entities, each with its own local memory, communicating via message passing over a backbone communication network.
Definition 2 (OS view): Multiple processors, each with its own local memory, communicating through high-speed buses or telephone lines.

The key enabler for distributed computing is seamless network connectivity between collaborating systems. The geographical span can range from a single lab to global boundaries.

Examples of Distributed Systems

The Internet ATM / banking networks Intranet workgroups Ubiquitous networked devices (IoT) Vehicular ad hoc networks (VANETs)
VANETs are a concrete modern example: smart vehicles with on-board communication units form spontaneous ad hoc networks when in proximity, executing safety, entertainment, or infotainment functions.

Types of Nodes in a Distributed System

Workstations
End-user machines used to perform computing tasks. The consumer end of the distributed system.
Server Systems
Machines that provide resources and services to other nodes. The provider side of the system.
Personal Assistance Devices
Handheld/mobile devices connected via wireless communication networks. Any communication paradigm may be used.

Properties & Advantages of Distributed Systems

PropertyExplanation
Fault Tolerance With multiple nodes, single node failures degrade performance but do not bring the whole system down. (A centralised system would go completely offline.)
Partial Role Execution Each node performs only its designated portion of the task — no single node bears the full workload.
Resource Sharing Compute resources (CPU, memory, storage) are shared across nodes in the system.
Load Balancing Work can be distributed across nodes to prevent bottlenecks — distinct from but related to resource sharing.
Scalability New nodes can be added to the network as demand grows — the system is easy to expand.
High Performance Parallel computing (a subset of distributed computing) enables tasks to run concurrently across nodes for speed gains.

Why Distributed Systems Are Needed

Application Nature
Some applications are inherently distributed — e.g. banking, internet services — and demand it by design.
Performance
Compute-intensive or data-intensive tasks benefit from parallel execution across multiple nodes.
Robustness
Mission-critical applications cannot afford a single point of failure — distributed systems eliminate this risk even if the workload itself is light.
Summary
Computing (ACM 2005): Any goal-oriented activity requiring computing machinery — spans hardware, software, AI, and communications across all user types.
Course Scope: Covers NIST model → cloud architecture → service models (IaaS/PaaS/SaaS) → deployment models → SLA → cloudonomics → resource management → data management → security → case studies → future trends.
Cloudonomics analogy: Buying vs. hiring compute is like buying vs. hiring a car — economical only above a certain usage threshold. Cloud is not always cheaper.
Data criticality: Unlike applications, lost data cannot be reinstalled — making cloud data security and backup mechanisms fundamentally more critical than application security.
Trust–Reputation–Risk triangle: These three factors are deeply interlinked in any cloud deployment and collectively govern how a CSP should be evaluated and trusted.

Evolution lineage: Distributed → Cluster → Grid → Utility → Cloud. These are not strictly sequential; each addressed specific needs and contributed building blocks to cloud computing.
