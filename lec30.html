Lecture 30 MED priority

Broker for Cloud Marketplace

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Introduces the cloud marketplace broker concept — an intelligent middleman that selects the best provider for a customer from multiple competing CSPs. Covers the broker architecture (monitoring, migration, trust calculation, selection modules) and applies a fuzzy inference engine for provider selection and migration decisions. Simulation results show fuzzy outperforms crisp broking on QoS metrics.

1 · Why a Broker?
Cloud marketplace problem: Many competing IaaS/PaaS/SaaS providers exist, each with different QoS promises, SLAs, trustworthiness, and pricing. A customer must select the best match — but lacks the tools, history, and monitoring capability to do this alone.
Flexible selection
Customer requirements are often fuzzy (not crisply defined). A broker translates vague needs into a quantitative match with provider offerings.
Trustworthiness evaluation
Trust is not binary — different trust values can be assigned per QoS parameter (availability, bandwidth, security). The broker aggregates these into a suitability score.
Vendor lock-in mitigation
A broker can trigger migration from one provider to another if experienced QoS falls below threshold — reducing dependency on any single vendor.
2 · Broker Architecture
Monitoring module
Continuously tracks provider performance
Monitors experienced QoS (availability, bandwidth) per VM per provider against promised values. Computes SLA satisfaction scores for each service instance at each provider: SLA satisfaction = experienced value / promised value per parameter.
Provider trust calculator
Historical trust per QoS parameter
Uses monitoring history to compute trust values per provider, per parameter (e.g., trust on availability = 0.8, trust on bandwidth = 0.6). Trust values are kept independent per parameter — they are not collapsed into a single number.
Provider selection (FIS)
Fuzzy matching of requirement to offering
Input: provider's offered QoS + trustworthiness. Output: suitability score for this customer's requirements. Customer request is dispatched to the provider with maximum suitability.
Migration decider (FIS)
Triggers provider switch when needed
Continuously evaluates degree of SLA satisfaction for the running service instance. If satisfaction < threshold, triggers migration to the next-best provider — selected through the same provider selection procedure.
3 · Fuzzy Inference Engine — How It Works
Why fuzzy? Customer requirements and provider offerings are not crisply defined — they involve linguistic terms like "good availability" or "acceptable latency." A crisp (binary yes/no) broker discards too many valid options; a fuzzy system handles partial membership.
Step 1: Fuzzification Convert crisp QoS inputs (provider offerings, customer requirements, trust values) into fuzzy membership values. Membership levels: extremely poor, very poor, medium, good, very good, excellent.
Step 2: Rule evaluation Apply rule set derived from customer requirements. E.g., IF availability is "good" AND trust is "very good" THEN suitability is "very good".
Step 3: Defuzzification Convert the fuzzy output (suitability) back to a crisp score for comparison across providers. Provider with highest suitability score is selected.
Crisp broker comparison: A conventional minimum-cost crisp broker makes binary decisions based solely on cost threshold. Simulation shows fuzzy broker tracks user requirements more closely on availability, bandwidth, cost, and response time — especially when some providers exhibit performance degradation.

Summary
Cloud broker role: An intelligent middleman that matches customer QoS requirements to provider offerings, monitors performance continuously, and migrates workloads when satisfaction drops below threshold.
Trust is per-parameter: Provider trust is evaluated separately for each QoS parameter (availability, bandwidth, etc.) — not as a single aggregate trust score.
Fuzzy inference: Fuzzification → Rule evaluation → Defuzzification. Handles the inherent vagueness of both customer requirements and provider descriptions better than binary crisp brokering.
Migration trigger: If experienced SLA satisfaction < predefined threshold for the current provider, the migration decider selects a new provider using the same fuzzy selection procedure and migrates the service instance.
