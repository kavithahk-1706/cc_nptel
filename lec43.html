Resource Management — II

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Deepens the resource management taxonomy from Lecture 42 with a focus on service placement, task offloading, and infrastructure for cloud-fog-edge. Introduces the service placement problem formally, taxonomy of placement strategies, a concrete vision-and-activity-recognition case study for application partitioning across edge/fog/cloud, and the two modes of offloading. Exam-relevant concepts: placement constraints, offloading types, centralized vs. distributed control.

1 · Service Placement Problem
Service placement problem: Given an application with multiple components and an infrastructure graph (edge nodes, fog nodes, cloud), find the optimal mapping of application components onto infrastructure nodes — satisfying resource constraints and optimization objectives (latency, cost, energy).

Why placement is non-trivial

Not all components need to run at the same tier. Some computations are best at the edge (low latency decisions), some at the fog (aggregation), and some at the cloud (global context, heavy ML inference). Fog computing is a highly virtualized platform — it must interoperate between end users / IoT devices and the cloud, and must support distributing the formerly centralized cloud workload to distributed edge nodes.

Placement Constraints

Constraint TypeDescriptionExample
Resource-levelInfrastructure has finite CPU, RAM, storage, bandwidth — a component cannot be placed on a node that cannot meet its minimum requirements.Face recognition requires ≥500MB free RAM — cannot run on a constrained gateway.
Network-levelLatency and bandwidth constraints between placement nodes must be satisfied.A real-time video analytics component cannot tolerate 200ms cloud round-trip.
Application-levelLocality requirements — some components must execute in a specific geographic or administrative domain.Patient data processing must stay within hospital network; delay-sensitive alarms must be handled locally.

Service Placement Taxonomy (four aspects)

Taxonomy
Control Plane Design
How the placement decision is made and enforced — centralized (single orchestrator) or distributed (collaborative fog nodes). Each has different scalability and failure characteristics.
Taxonomy
Placement Characteristics
What properties the placement algorithm optimizes and enforces — latency bounds, resource fit, locality, SLA compliance.
Taxonomy
System Dynamicity
How the placement adapts to changing conditions — static placement vs. dynamic re-placement triggered by resource fluctuations or mobility events.
Taxonomy
Mobility Support
Whether the system tracks device movement and migrates services accordingly — critical for vehicular networks and ambulance scenarios; less so for static sensor deployments.
2 · Case Study — Vision & Activity Recognition Application

A multi-component application worn by a user (e.g., Google Glass) illustrates how different components map to different tiers:

Component → Edge Device
Vision Capture
Camera on the wearable device. Runs locally — no choice, sensor is at the edge.
Component → Edge Device
Coarse Feature Extraction
Lightweight preprocessing of the raw image. Can run on the device itself (Google Glass) or a nearby connected device (laptop acting as edge compute).
Component → Fog (Smart Wi-Fi Gateway)
Object Recognition
Needs more resources than the wearable has; runs on a LAN router or smart Wi-Fi gateway acting as fog. Moderate compute but not heavy ML.
Component → Fog or Cloudlet
OCR (Character Recognition)
Can run on smart gateway or a cloudlet (a small cloud instance near the edge). Requires more compute than object recognition.
Component → Cloud
Face Recognition
Resource-intensive; requires comparing against large databases. Offloaded to cloud back-end. Cannot run on a simple fog gateway.
Component → Cloud
Learning-based Activity Inference
Requires heavy ML models, possibly external datasets for inference. Must run at the cloud — may also need data from other sources not available at fog.
Component → Fog (Smart Gateway)
Rendering
Assembles results and creates display output. Runs at the smart Wi-Fi gateway, which returns the rendered result to the wearable device for display.
Insight from case study: Distributing components across edge/fog/cloud (rather than sending everything to the cloud) achieves lower latency, better scalability, and mobility support — if the user moves, a nearby fog node takes over rendering and local processing without re-establishing cloud connections for every component.
Caveat: Application partitioning and placement is application-specific. There is no universal mapping — it depends on compute requirements, resource availability at each tier, and latency constraints per component.
3 · Task Offloading
Offloading: Moving computation from where it would naturally execute to another tier that can perform it more efficiently. Brings cloud-side services closer to the data source to reduce latency and bandwidth usage.
User Device → Edge (Augmentation)
DirectionFrom end device to nearest edge node
HopsTypically single-hop (direct connection)
PurposeAugment compute-limited user devices by offloading intensive tasks to nearby edge node
MechanismsApplication partitioning; caching mechanisms
Cloud → Edge (Server Offload)
DirectionFrom cloud to edge nodes at the network periphery
HopsMultiple hops; requires coordination
PurposeMove cloud-executed workloads closer to users/data sources for latency and bandwidth reduction
MechanismsServer replication, server partitioning across edge, content popularity-based or multi-layer caching
Partial vs. full offloading: A task can be fully offloaded (entire computation moves to edge/fog) or partially offloaded (split — some components stay on the device, some move to the fog). After partial offloading, results from both must be reassembled (ensembled/aggregated) before delivery to the user.
4 · Control Mechanisms — Centralized vs. Distributed
Centralized Control
StructureSingle orchestrator manages all fog/edge nodes
AlgorithmsSolver-based approaches; graph matching; ILP
Best forSmall, static deployments; few fog nodes in controlled area
RiskSingle point of failure; scalability bottleneck at the controller
Distributed Control
StructureEach fog node (or cluster) manages itself collaboratively
AlgorithmsGame theory; genetic algorithms; blockchain-based; distributed optimization
Best forLarge-scale, mobile deployments; vehicular networks
RiskCoordination overhead; consistency challenges across nodes
5 · Infrastructure: Hardware, System Software, Middleware
Hardware
Low-power, small form-factor devices: mobile devices, routers, gateways, home servers, edge ISP servers, vehicles, drones. Cloud has abundant resources; fog leverages surplus resources on existing network devices rather than dedicated infrastructure.
System Software
Runs on fog/edge hardware; manages compute, network, and storage resources. Must support multi-tenancy and isolation (multiple applications sharing a fog node). Includes: OS, virtualization (VMs and containers), network virtualization (SDN, NFV), and overlay networks.
Middleware
Sits above the OS; provides what system software does not: performance monitoring, coordination of distributed computing nodes, orchestration, VM/container deployment across fog nodes, communication protocol support. Enables faithful, reliable, scalable fog operation.

Virtualization at the Fog Layer

System Virtualization
VMs and Containers
Standard virtualization techniques brought down to fog hardware. VM and container migration is a critical research area — moving a running computation to another fog node when a device is mobile or a node is overloaded.
Network Virtualization
SDN and NFV
Software Defined Networking (SDN) separates control plane from data plane — enables flexible, programmatic network management across fog nodes. Network Function Virtualization (NFV) replaces dedicated network hardware with software running on commodity devices. Both are proliferating in modern networks.
Summary
Service Placement: Maps application components to infrastructure nodes under three constraint types — resource-level (capacity), network-level (latency/bandwidth), and application-level (locality/deadline). Requires an orchestration engine to manage placement decisions.
Application Partitioning: A single application's components should be split across edge, fog, and cloud based on compute requirement and latency sensitivity — not all-or-nothing. The vision recognition case study demonstrates this clearly.
Offloading: Two types — user device → edge (augments resource-limited devices) and cloud → edge (reduces cloud load and latency). Partial offloading splits a task and requires reassembly of results.
SDN and NFV: Both are key enablers for flexible fog/edge management — SDN for programmable network control, NFV for running network functions in software on commodity hardware rather than dedicated appliances.
