Lecture 32 MED priority

Mobile Cloud Computing – II

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Deep-dives into the task partitioning problem for mobile offloading — the call-graph model, ILP formulation, energy-saving conditions, and the cloudlet architecture. Covers MAUI and COMET research systems. Key exam material is the energy-saving formula and the conditions under which offloading is beneficial.

1 · The Core MCC Problem — Task Partitioning
Task partitioning problem: Given an application, decide which methods/modules execute locally on the mobile device and which are offloaded to the cloud — to minimize energy consumption while keeping total execution latency within a threshold T.
Static Partitioning
WhenDecided once at app launch
MethodILP solver invoked at startup
HeuristicsPre-launch estimation of energy consumption
LimitationCannot adapt if environment or workload changes during execution
Dynamic / Adaptive Partitioning
WhenRe-evaluated continuously during runtime
MethodCost graph + branch-and-bound; profiling at procedure-call level
Adapts toVarying bandwidth, changing data, remote resource availability
ChallengeScheduling + resource management across independently owned infrastructure

Call-graph model

The application is represented as a call graph where nodes are methods/tasks:

Native nodes
Must run on device
Some methods (e.g., hardware-dependent, sensor access) cannot be offloaded. These are fixed to the device in the graph.
Remoteable nodes
Can run on device or cloud
The optimizer decides. Edges represent execution dependencies — a method cannot start until its predecessor completes.
Node cost (local)
Energy to run locally
Energy consumed executing the method on the mobile device.
Edge cost (transfer)
Energy to transfer + receive
Energy consumed transmitting program state/data to the remote server (and receiving results). Cloud-side execution energy assumed negligible compared to device energy.
2 · Energy Saving Formula — When to Offload

Variable definitions

SymbolMeaning
PcEnergy cost per second when mobile phone is computing
PiEnergy cost per second when mobile phone is idle
PtrEnergy cost per second when mobile phone is transmitting data
CNumber of instructions to execute
MSpeed of mobile device to compute C instructions (instructions/sec)
S = F·MSpeed of cloud server; F = how many times faster the cloud is than the mobile
DTotal data to transmit
BAvailable bandwidth (data/sec)

Energy saved by offloading

Energy saved = Energy (local) − Energy (offloaded)

Local execution energy: Pc · (C/M)

Offloaded execution energy: Pi · (C/S) + Ptr · (D/B)
— idle while cloud computes, plus transmit cost

Substituting S = F·M:

Energy saved = (C/M) · [Pc − Pi/F] − Ptr · (D/B)

Offloading is beneficial when this expression is positive.

Conditions for offloading to save energy

Condition 1
D/B must be small compared to C/M
Data transfer time (D/B) must be much smaller than local compute time (C/M). If you spend more energy transmitting than you save by offloading — don't offload.
Condition 2
F must be sufficiently large
The cloud must be significantly faster than the mobile device. If F is small (cloud only slightly faster), the energy saving margin disappears.
Not all applications benefit from offloading. Apps with large data-to-computation ratios (high D, low C) are poor offloading candidates. Cloud services for mobile must also account for energy overhead of privacy, security, reliability, and data communication beyond this simple formula.
Golden rule: Offloading is beneficial when large computation (C) is needed with relatively small data communication (D). Computation-heavy, data-light tasks are ideal candidates.
3 · Research Systems — MAUI and COMET
MAUI
Full nameMobile Assistance Using Infrastructure
ApproachProgrammer annotates each method as remoteable or not
Source codeRequired — annotations needed
ArchitectureMAUI client (mobile) + MAUI server (cloud); profiler + solver partition app; RPC calls between sides
DecisionFramework uses annotations + profiling to decide whether to execute method on cloud to save energy and reduce time
COMET
Full nameCode Offloading by Migrating Execution Transparently
ApproachWorks on unmodified applications — no source code required, only binaries
Source codeNot required
ArchitecturePhone OS + Remote OS with Distributed Shared Memory (DSM) model
DSMPhysically separate memories addressed as one logical shared space — allows transparent thread migration across machines
OptimizationOnly sends modified heap portions (not full heap) during migration — reduces data traffic
4 · Cloudlets — Reducing Offloading Latency
Cloudlet: A trusted, resource-rich computer or cluster that is well-connected to the internet and available for use by nearby mobile devices. Essentially a "small cloud" close to the user.
Remote Cloud Full-scale cloud infrastructure; high latency; multiple hops
Cloudlet (Middle Tier) Resource-rich, nearby; single-hop via Wi-Fi/short-range radio; low latency; reduces energy overhead
Mobile Devices Resource-constrained SMDs; offload to cloudlet instead of distant cloud
Latency advantage
Single-hop network
Reaching cloudlet via Wi-Fi or short-range radio — one hop instead of many — dramatically reduces round-trip latency compared to offloading to a remote cloud datacenter.
Energy advantage
Lower transmission cost
Wi-Fi transmission is more energy-efficient than cellular/mobile network transmission. Shorter distance + fewer hops = less Ptr · (D/B) energy cost.
Cloudlet architectural role: Middle tier in a 3-tier architecture (Mobile Devices → Cloudlet → Cloud). Cloudlets reduce latency for offloading-sensitive applications and improve the energy-saving math by lowering transmission costs.
5 · Key Challenges in MCC
ChallengeCategoryDescription
Low bandwidthCommunicationWireless radio spectrum is scarce compared to wired networks; bandwidth varies over time and location

HeterogeneityCommunicationWireless connectivity spans many heterogeneous networks; achieving always-on, on-demand, energy-efficient connectivity is hard

Totality requirement: MCC cannot be solved in isolation — energy saving, latency, security, reliability, and heterogeneity must all be considered together to give the mobile user a seamless experience.
Summary
Task Partitioning: The core MCC problem — split app methods between device (native/mandatory) and cloud (remoteable); modeled as a call graph; minimize energy subject to latency constraint L.
Energy-saving condition: Offload when C (computation) is large and D/B (transfer time) is small. Cloud must be F times faster where F is sufficiently high. Formula: Energy saved = (C/M)·[Pc − Pi/F] − Ptr·(D/B) > 0.
MAUI vs COMET: MAUI requires annotation but offers fine control; COMET works on unmodified binaries using DSM for transparent thread migration.
Cloudlets: Middle-tier architecture — nearby resource-rich mini-clouds reachable in one hop via Wi-Fi, reducing latency and transmission energy compared to offloading to a distant cloud.
Not always beneficial: Offloading is a net loss when data transfer cost exceeds compute savings — must evaluate per application and per network condition.
