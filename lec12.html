Lecture 12 HIGH priority

Economics of Cloud Computing

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Covers the economic rationale for cloud adoption — when cloud is cheaper than owned infrastructure, how statistical multiplexing smooths demand, the mathematics of utility pricing and penalty cost, and when to use hybrid models. Quantitative and formula-heavy; expect exam questions on CV, utility premium, and the break-even condition.

1 · Cloud Economic Properties
Common Infrastructure
Pooled, standardized resources shared across tenants. Benefits come from statistical multiplexing — not all tenants peak simultaneously, so the same hardware serves more workloads than dedicated provisioning allows.
Location Independence
Services come to the user rather than users going to the compute. Enables global reach but introduces latency as a design constraint — human-perceptible threshold is 10–100 ms; VOIP tolerance ~200 ms.
Utility Pricing + On-Demand
Pay-per-use model (like electricity). Resources provisioned and de-provisioned on demand with minimal human involvement. Eliminates permanent peak-sizing of owned infrastructure.
Core problem with owned infrastructure: You must size for peak demand. Peak-sized hardware is expensive, underutilized most of the time, and obsolete within 3–5 years.
2 · Economies of Scale
Overhead Reduction
Reduced per-unit overhead
Ownership costs — power (UPS, AC), maintenance (AMC), human resources — often exceed original equipment cost over the asset life. Cloud providers amortize this across thousands of tenants.
Multiplexing Benefit
Build below peak, serve above average
Diverse tenants rarely peak simultaneously. The same hardware serves more aggregate demand than any single tenant justifies, driving down cost per delivered resource.
Peak-sized Build
Infrastructure built to peak
Multiplexing diverse demand gives higher utilization and lower cost per delivered resource than unconsolidated workloads. SLA violation payout risk is reduced.
Sub-peak Build
Infrastructure built below peak
Multiplexing reduces unserved demand (blocking). Good scheduling manages priority. Lower revenue loss from SLA violations vs. single-tenant scenario.
3 · Coefficient of Variation (CV)
Definition: CV = σ / |μ| — ratio of standard deviation to the mean. Measures relative variability of demand. Lower CV = smoother, more predictable demand = easier to provision for.

Effect of multiplexing on CV

Let X₁, X₂, …, Xₙ be independent, identically distributed demands each with mean μ and std dev σ:

QuantitySingle demandAggregate of n demands
Meanμnμ
Varianceσ²nσ²
Std deviationσ√n · σ
CVσ/μ(1/√n) · (σ/μ)
Key result: Aggregating n independent demands reduces CV by 1/√n. Aggregating 100 workloads cuts CV by 90%. This is why large cloud providers run infrastructure at far higher utilization than any single organization could.

Negative correlation — customer segment selection

A provider can select customers with negatively correlated demand (e.g., daytime-heavy vs. nighttime-heavy workloads). Demands compensate each other over time, letting the same infrastructure serve both at near-full utilization.

Perfectly correlated demand: If all tenants peak at the same time, aggregate CV stays constant — no multiplexing benefit. Provider must size for the full combined peak.
4 · Value of Location Independence

Cloud reverses the old paradigm — compute power comes to the user via thin clients over wired, wireless, or satellite networks.

Latency constraint: Human perception threshold 10–100 ms. Speed of light in fiber ≈ 124 miles/ms. VOIP unusable above ~200 ms. Latency grows with distance and number of hops.

Supporting a global user base requires a dispersed service architecture — multiple geographically distributed data centers — which introduces CAP theorem trade-offs (Consistency, Availability, Partition tolerance) and significant capital investment.

5 · Value of Utility Pricing — Mathematical Model

Variable definitions

SymbolMeaning

PPeak demand

BBaseline (owned) unit cost per unit time

UUtility premium = C/B

Cost comparison

ModelTotal cost over TNotes
Cloud costU · B · ∫D(t)dtPay only for what you consume
Owned costP · B · TPay for peak capacity for the full period
Break-even condition — cloud is cheaper when:
U · B · ∫D(t)dt < P · B · T  ⟹  U < P · T / ∫D(t)dt  ⟹  U < P/A

Cloud is cheaper when the utility premium is less than the peak-to-average demand ratio.
Car analogy: Daily commuter should buy a car. Occasional traveler should rent. Same logic: if your demand is near-constant (A ≈ P), own infrastructure. If demand is spiky (P ≫ A), go cloud.

Exponential demand — the math:
D(t) = eᵗ, provisioning delay = t_p → D(t) − R(t) = k₁ · eᵗ → Penalty = c · k₁ · eᵗ

Penalty grows exponentially. Static provisioning can never keep up. Only elastic cloud on-demand provisioning can track exponential demand.
Summary
Statistical Multiplexing: Aggregating n independent workloads reduces CV by 1/√n — higher utilization, lower per-unit cost.
Break-even Rule: Cloud is cheaper when U < P/A. The higher the peak-to-average demand ratio, the stronger the case for cloud.
Negative Correlation: Selecting customers with offsetting demand profiles lets a provider run near-full utilization on the same hardware.
Exponential Demand: Static provisioning strategies produce exponentially growing cost penalties. Elastic on-demand is the only viable solution.
Hybrid Models: Own baseline capacity, burst to cloud for spikes. Always factor in network cost, interoperability overhead, and reliability — not just unit cost.
