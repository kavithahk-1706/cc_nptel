Lecture 36 HIGH priority

Introduction to Docker Container

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Introduces Docker container technology — what containers are, how they differ from virtual machines, and why they matter for cloud computing. Covers the core philosophy of "develop, ship, run anywhere," the Docker architecture (engine, image, container, hub), and how containers sit on top of cloud IaaS. Conceptual and definitional; key differences between VMs and containers are exam-ready content.

1 · The Portability Problem
Core challenge: When you move a software application from one environment to another (laptop → server → cloud → mobile), it typically requires recompilation, reconfiguration, or redevelopment. As the number of application types and target environments grows, the combinatorial effort becomes unmanageable.

The problem manifests as a compatibility matrix: for every application (static website, background worker, user DB, analytics DB, API endpoint, web frontend, …) × every platform (laptop, server, Android, iOS, cloud, smart watch), you need a different build. The goal is to make every cell in that matrix a checkmark with minimal effort.

Shipping container analogy (from lecture): Before standardized shipping containers, moving a piano required different equipment than moving a barrel or a car. The industry solved this by defining a standardized container — any product packed inside it can be handled by any crane, truck, ship, or rack. The same logic applies to software: if the application is bundled into a standardized container, any platform that can run the container can run the application — regardless of what is inside.
Container solution: Bundle the application together with all its dependencies (libraries, binaries, runtime, environment variables, config files) into a self-contained unit called a container. The infrastructure only needs to support the container format — it does not need to know what is inside.
2 · Docker — Overview
Docker: An open-source container management service. Initial release: March 2013. Core philosophy: Develop → Ship → Run Anywhere. A Docker container can be deployed on any desktop OS (Mac, Linux, Windows), any cloud platform (OpenStack, Azure, AWS, Google Cloud, IBM Bluemix), and even on Android devices — without modification.
Docker vs Cloud: Docker is not a competitor to cloud — it is a complementary technology. Cloud can act as a platform to host Docker containers (IaaS running containers via Docker engine on VMs), enhancing cloud's capability by adding application-level portability.

Key Features

Portability
Run Anywhere
A Docker container runs identically on a developer's laptop, a QA server, a production cloud VM, or an Android device — eliminating the "works on my machine" problem. No recompilation needed per target environment.
Lightweight
Smaller Footprint
Container images are typically tens of MBs. Containers share the host OS kernel — no separate guest OS per container. They start almost instantaneously and require far fewer resources than VMs.
Isolation
Process Isolation
Each container runs as an isolated process in user space. It accesses the host filesystem and ports only if explicitly configured to do so — default is fully isolated.
Scalability
Easy to Scale
Because containers are lightweight, spinning up many instances of the same container is fast and resource-efficient. Scaling up is not constrained by the overhead of full OS provisioning.
Collaboration
Dev/QA/Ops Alignment
Development, QA, and operations teams all work with the same container image. Environment differences between teams are eliminated — the container is the shared artifact.
Versioning
Incremental Updates
Docker images are layered. A modification to container A produces container A' that stores only the diff — not a full copy of the image. This saves storage and makes updates efficient.
3 · Docker Architecture vs Traditional Virtualization
▶ 18:42
Worth watching: Side-by-side architecture diagram — traditional VM stack (server → host OS → hypervisor → guest OS → app) vs Docker stack (server → host OS → Docker engine → containers with apps).
Traditional Virtualization (VM)
StackPhysical server → Host OS → Hypervisor (VMM) → Guest OS → Application
Guest OSEach VM has its own full guest OS (Linux, Windows, etc.)
Resource useHeavy — each VM includes a full OS image; disk, RAM, CPU overhead per VM
StartupMinutes — OS boot sequence per VM
IsolationFull hardware-level isolation via hypervisor
Image sizeGBs (includes OS)
PortabilityVMs can be moved between hypervisors but carry the full OS
Docker Containers
StackPhysical server → Host OS → Docker engine → Containers (app + deps)
Guest OSNone — containers share the host OS kernel
Resource useLight — only app-layer code and dependencies bundled; no per-container OS
StartupSeconds or less — no OS boot; container process starts directly
IsolationProcess-level isolation in user space; shares kernel
Image sizeTens of MBs (no OS)
PortabilityRuns on any host with Docker engine — regardless of underlying OS or cloud
Trade-off: VMs provide stronger hardware-level isolation (separate kernel per VM). Containers share the host kernel — a kernel vulnerability can affect all containers. For security-critical multi-tenant workloads, VMs remain preferred; for developer portability and microservice deployment, containers win on efficiency.
4 · Images vs Containers
Docker Image
DefinitionA lightweight, standalone, executable package
ContentsCode, runtime, libraries, environment variables, config files — everything needed to run the software
StateStatic — a blueprint; does not run on its own
StorageStored in Docker Hub (registry) or local image store
AnalogyA class definition or an executable binary on disk
Docker Container
DefinitionA runtime instance of an image — what the image becomes in memory when executed
ContentsImage layers + a writable container layer for runtime state
StateRunning process — isolated from the host by default
AccessOnly accesses host filesystem/ports if explicitly configured
AnalogyA class instance — an object created from the image blueprint
Key point: Multiple containers can run simultaneously from the same image, each in an isolated process. Each container takes no more memory than a running executable — no per-instance OS overhead.
5 · Docker Components
Runtime
Docker Engine
The core daemon that builds Docker images and creates/runs Docker containers. Runs on top of the host OS (Linux, Mac, Windows). Analogous to a hypervisor in the VM world — sits between the OS and the containers.
Registry
Docker Hub
Public repository of Docker images (hub.docker.com). Developers publish images here; users search and pull images. Docker Hub can automatically build images from Dockerfiles hosted on GitHub.
Build Script
Dockerfile
A text script that defines how to build a Docker image automatically. Can be version-controlled in Git or SVN alongside source code. Docker Hub can trigger automated builds when a Dockerfile in GitHub changes.
Composition
Docker Compose
A tool to define and run multi-container Docker applications. Allows an application composed of multiple services (web frontend, database, queue) to be described as a single configuration file.
Platform
Docker for Mac / Windows / Linux
Platform-specific Docker distributions. Each provides the Docker engine adapted for that OS, allowing developers to run containers on their local machine during development without a separate Linux server.

7 · Docker on Cloud
▶ 27:42
Worth watching: Diagram showing Docker containers running inside VMs on a cloud IaaS layer — hypervisor → guest OS → Docker engine → containers. Illustrates how cloud and containers are complementary, not competing.

Cloud acts as the IaaS platform on which Docker containers are deployed:

Physical Infrastructure Cloud data center hardware — servers, storage, network
Hypervisor / VMM Virtualizes hardware → provides Virtual Machines (IaaS layer)
Guest OS on VM Linux or Windows running inside each VM
Docker Engine Container runtime running on the guest OS — manages images and containers
Docker Containers Application + dependencies, isolated per container — deployed across cloud VMs

Who Uses Docker and Why

Developers
Eliminate the "works on my machine" problem. Share a container image with teammates — exact same runtime environment for all, regardless of their local OS.
Operators
Run and manage multiple applications side-by-side in isolated containers on the same host. Better compute density than one-application-per-VM.
Enterprises
Build agile software delivery pipelines — build once, deploy to any environment (dev, QA, staging, production on any cloud). Works for Linux, Windows Server, and Linux-on-mainframe apps.
Summary
Portability Problem: Moving software between environments requires recompilation/reconfiguration — Docker solves this by bundling app + all dependencies into a standardized container.
Image vs Container: An image is a static blueprint (code + dependencies); a container is a running instance of that image — analogous to class vs object. Multiple containers can run from one image, each isolated.
Container vs VM: Containers share the host OS kernel (no per-container guest OS), are lightweight (tens of MBs vs GBs), start in seconds, and provide process-level isolation. VMs provide stronger hardware-level isolation but at far greater resource cost.
Docker on Cloud: Docker and cloud are complementary — cloud (IaaS) provides the VM platform; Docker engine runs on VMs; containers run on the Docker engine. Cloud becomes a portable, scalable host for containerized applications.
Security Trade-off: Containers share the host kernel — a kernel-level vulnerability can compromise all containers on the same host. VMs maintain stronger isolation for multi-tenant security-critical workloads.
