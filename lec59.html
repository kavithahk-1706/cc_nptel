Case Study II: Internet of Health Things (Part A)

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Case study demonstrating the cloud-fog-edge-IoT continuum applied to health monitoring applications. Covers the motivation for moving computation from cloud to edge/fog, the IoHT framework design, four-layer topology, workflow, and a comparison of cloud-only vs. fog-edge-cloud architectures. Uses iFogSim simulator. For demonstration only — no medical/clinical implications.

1 · The Cloud-to-Things Continuum
Cloud-to-things continuum: Rather than treating cloud, fog, edge, and IoT as separate isolated layers, the modern view treats them as an integrated, hierarchical framework — each layer processes what it can at its own level, and only passes what is necessary up the hierarchy. Orchestration across layers determines overall system efficiency.
IoT / Body Sensor Layer Sensors, actuators — data originates here. Limited processing power, limited storage, no global view of the environment
Edge Layer (Mobile Device) Smartphone or embedded gateway. Collects data from one or a few sensors, performs real-time local processing, displays alerts to user. Minimum latency to source.
Fog Layer (Area Gateway / ISP) Local network node (router, area gateway, Raspberry Pi). Aggregates from multiple edge nodes, performs data filtering, data processing, and event handling for a geographic region. Intermediate latency.
Cloud Layer Centralized data center (AWS, Google Cloud, IIT KGP Megamala). Business analytics, global-scale decisions, long-term storage, confirmatory processing. Highest latency, maximum resources.
Temperature sensor example: A single corner sensor showing high temperature may report "normal" from its local view. A fog node seeing all 10–20 room sensors simultaneously can compute room-wide mean/variance and identify a hot zone caused by a nearby server — a decision impossible at the individual sensor level. Aggregation at fog gives a better global view than any individual IoT device can.
2 · Cloud-Only vs. Edge-Only Limitations
Cloud-only Challenges
LatencyAll data must travel to remote CDC and back — high round-trip time
BandwidthMassive IoT data volumes require constant high-bandwidth upstream links
Real-timeHigh latency makes true real-time response impractical for time-critical applications
CostAll processing charged as cloud subscription — cost scales with volume
AdvantageSimple setup, near-infinite resources, management responsibility with provider
Edge-only Limitations
ResourcesLimited processing power, memory, and storage at edge devices
Global viewEach edge device only sees its own sensors — no aggregate perspective
AnalyticsCannot perform complex analytics or model training
StorageCannot store historical data for trend analysis
AdvantageMinimum latency, no network cost for local decisions, privacy by default
Benefits of fog/edge-cloud hybrid: Reduced latency (processing closer to source), less network congestion (aggregation reduces upstream data volume), lower cloud subscription cost (fewer operations sent to cloud), better handling of location-aware real-time applications, improved data privacy (raw sensitive data never leaves local network).
3 · IoHT Case Study — Design and Objective
Internet of Health Things (IoHT): Application of the IoT paradigm to health monitoring — body sensors collect health parameters (pulse, BP, activity) and feed them through a cloud-fog-edge pipeline for analysis, alerting, and logging. Disclaimer: for demonstration only; no medical or clinical implications.

Objectives

Goal 1
Design fog-edge-cloud health model
Design and simulate a fog-based healthcare model to reduce latency, network usage, and cloud cost compared to a cloud-only model.
Goal 2
Simulate with iFogSim
Use iFogSim (open-source fog/edge simulator, developed jointly by IIT Kharagpur and University of Melbourne, now maintained by University of Melbourne) to evaluate feasibility before hardware implementation.
Goal 3
Build customized wearable device
Fabricate a custom body sensor collecting health parameters (accelerometer for activity, pulse/BP sensors) and transmit data through the multi-tier pipeline: body sensor → mobile (edge) → fog (area gateway) → cloud.
Goal 4
Evaluate DEW computing integration
Explore DEW (Dew) computing — on-premise computing that functions independently of cloud connectivity and syncs when reconnected — as an additional layer for resilience when cloud connectivity is unavailable.
4 · IoHT Network Topology and Workflow

Four-Layer Network Topology (latency decreases upward)

LayerComponentRoleRelative Latency
Cloud (Level 0)AWS / Megamala CDCGlobal analytics, confirmatory module, long-term storageMaximum (ISP gateway → cloud hop = 100 units)
Fog (Level 1)Area gateway / ISP nodeData filtering, data processing, event handlingMedium (area → ISP = 2 units)
Edge (Level 2)Mobile smartphoneClient module, data collection from body sensors, display alertsLow (mobile → area gateway = 2 units)
IoT (Level 3)Body sensorsPulse, BP, accelerometer data collectionMinimum (sensor → mobile = 1 unit)

Application Workflow

Body Sensors Collect raw health parameter data (BP, pulse, accelerometer x/y/z axes)
Client Module (Mobile / Edge) Receives raw data; in fog-based model, placed at the mobile device (edge)
Data Filtering Module (Fog) Cleans and pre-processes data at fog/area gateway; in cloud-only, this is pushed to cloud
Data Processing + Event Handler (Fog / Cloud) Processes filtered data; raises events/alerts; in cloud-only, both modules are in cloud
Confirmatory Module (Cloud) → Display (Mobile) Cloud confirms events against knowledge base; alert displayed on user's mobile device ("Normal" / "Visit doctor")
5 · Application Placement: Fog-Edge-Cloud vs. Cloud-Only
ModuleFog-Edge-Cloud PlacementCloud-Only Placement
Client moduleMobile (edge)Mobile
Data filteringArea gateway (fog)Cloud
Data processingArea gateway (fog)Cloud
Event handlerArea gateway (fog)Cloud
Confirmatory moduleCloudCloud
DisplayMobileMobile
Trade-off: Fog-edge-cloud distributes the processing load, reducing latency and cloud cost — but requires the organization to own, configure, and maintain the fog and edge infrastructure. Cloud-only is simpler to manage (provider's responsibility) but costlier and slower for real-time health monitoring applications.
Summary
Cloud-to-things continuum: Not isolated layers — integrated, hierarchical, orchestrated framework where each level processes what it can to minimize latency, network usage, and cloud cost.
Fog/edge benefits: Reduced round-trip latency, less upstream bandwidth, lower cloud subscription cost, better real-time response, enhanced data privacy (raw data stays within local network).
iFogSim: Open-source fog/edge simulator, developed by IIT Kharagpur + University of Melbourne. Use it to validate a multi-tier IoT architecture before hardware implementation.
Cost of fog/edge: Organization must own, configure, and maintain fog/edge infrastructure. Proper orchestration across layers is complex. Cloud-only is simpler to manage but performs worse for real-time IoT applications.
