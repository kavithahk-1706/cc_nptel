Lecture 13 HIGH priority

Managing Data in Cloud

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Covers why conventional relational databases don't scale to cloud workloads, then walks through the cloud-native alternatives: parallel DB architectures, Google File System (GFS) / HDFS, BigTable, Amazon Dynamo, and key-value data stores. Multiple distinct systems covered — each is individually exam-relevant.

1 · Why Traditional RDBMS Falls Short at Cloud Scale

At small scale, standard SQL databases work fine on a VM. At large scale — massive parallel read/write, enormous data volumes — they hit fundamental limits. Cloud data management requires different strategies.

RDBMS Architecture (quick recap)

Query Layer
RDBMS Parser + Optimizer
Transforms SQL queries into disk/memory operations. Optimizes execution order — e.g., doing SELECT before JOIN on two large tables dramatically reduces rows being joined.
Storage Layer
Disk Space Management
Stores records on contiguous memory pages to minimize disk seeks. Uses pre-fetching and page replacement policies. Data for a single query is stored physically close together.
FS Layer
Database File System
Independent of the OS file system — gives the DB full control over memory page management. Supports parallel I/O via RAID arrays (RAID 1, 2, 5, 6) across multiple disks. Files can span multiple disks for large storage.
Index Structure
B+ Tree
Primary access method — records stored in B+ tree indexed by primary key on specific columns. Efficient for point lookups and range queries on structured data.

Row-oriented vs Column-oriented storage

Row-oriented (traditional)
StoresComplete tuples contiguously
Best forTransaction processing — INSERT, UPDATE, DELETE of individual records
IndexesB+ tree on primary/secondary keys
ExamplesOracle, DB2, SQL Server
Column-oriented
StoresEach column family separately
Best forAnalytics / data warehouse — aggregation over millions of rows across specific columns
IndexesJoin indexes linking column projections
ExamplesVertica, Teradata, Netezza
2 · Parallel Database Architectures
▶ 12:16
Worth watching: The three architecture diagrams (shared memory / shared disk / shared nothing) are much clearer visually than described in text.
Shared Memory
Multiple CPUs share a single memory address space. Managed by SMP OS. Best for multi-CPU servers with compact, frequently accessed data. Limited scalability — memory becomes a bottleneck.
Shared Disk
Independent servers each with their own CPU, connected to shared storage (NAS or SAN) over high-speed Ethernet/fiber. Hybrid approach — processors work independently but share the data layer.
Shared Nothing
Fully independent servers, each with own CPU and disk, connected by a high-speed backbone network. Maximum scalability — no shared resource bottlenecks. Tables partitioned and distributed across nodes. Used in large cloud deployments.
Parallel RDBMS features: SQL optimizer handles distributed joins. Distributed 2-phase commit locking for transaction isolation. Fault tolerance via standby systems. Tables partitioned across nodes for parallel execution.
3 · Google File System (GFS) and HDFS
Purpose: Manage very large files (potentially terabytes) on large distributed clusters of commodity Linux servers connected by high-speed networks. Designed to handle failures during read/write as a normal operating condition, not an exception.
HDFS (Hadoop Distributed File System) is the open-source implementation of GFS architecture, available on Amazon EC2.

Key design points

Large files on commodity servers Fault tolerant by design Parallel reads, writes, appends Multiple simultaneous clients
Why commodity servers? P(system failure) = 1 − (1 − P(component failure))^N. With large N, individual failures are statistically certain — so the system must tolerate them, not try to prevent them with expensive hardware.

Architecture components

GFS termHDFS termRole
MasterNameNodeSingle logical master. Controls the namespace (metadata — where data is stored, replica locations). Does not store data itself.
Chunk ServerDataNodeCommodity Linux servers that store the actual data chunks. Each chunk replicated 3× on different physical racks.
ChunkBlockLarge files split into fixed-size chunks, stored across chunk servers. Each chunk identified by an offset.

Read operation

1. Client → Master Client sends full file path + offset to master/NameNode
2. Master → Client Master replies with metadata for one replica of the relevant chunk
3. Client caches metadata Client caches the chunk metadata for faster subsequent access
4. Client → Chunk Server Client reads data directly from the designated chunk server (any replica will do)

Write / Append operation

1. Client → Master Client sends file path; master replies with metadata for ALL replicas of the chunk
2. Client → All Chunk Servers Client pushes data to ALL chunk servers simultaneously
3. Chunk servers acknowledge Each chunk server acknowledges receipt of data
4. Master assigns Primary Master designates one chunk server as the primary
5. Primary appends + propagates offset Primary appends data at a chosen offset, sends that offset to replicas. All replicas must write at the same offset. If any fail, client retries. Append can go beyond EOF to handle simultaneous writers.
Why same offset across all replicas? Reads are served by any replica. If replicas have data at different offsets, a read would return inconsistent results depending on which replica answers. Consistent offsets ensure all replicas are identical.

Fault tolerance

Heartbeat Messages
Master monitors chunk servers
Master maintains regular "are you alive?" communication with all chunk servers. On failure detection, chunk server metadata is updated to mark it as failed — future requests won't be routed there.
Primary Failover
Master assigns new primary
If the primary chunk server fails, master assigns a new primary from the remaining replicas. Clients periodically retry failed chunk servers and update their cached metadata from the master.
4 · BigTable
BigTable is a distributed structured storage system built on top of GFS. It is not a relational database — it is a sparse, distributed, persistent multi-dimensional sorted map.

Data model

Data is accessed by three keys: row key + column key + timestamp. Multiple versions of the same cell are stored in decreasing timestamp order.

Column families: Each column stores arbitrary name-value pairs grouped into a column family. The set of column families is fixed when the table is created. Labels within a column family can be added dynamically at any time.

Architecture

Master Server
Metadata registry
Acts as a metadata repository — not a data server. Each large table is split into ranges called tablets. If the metadata itself becomes too large, it is also broken into tablets with a root tablet acting as coordinator.
Tablet Server
Data manager
Each tablet is managed by a tablet server. Stores each column family for a given row range in a separate distributed file called an SSTable. Supports large parallel reads and inserts, even simultaneously on the same table.
Insert vs Append: Insertions require finding the right sorted position and shifting data — more expensive than appends, which always add to the end. BigTable minimizes this overhead by storing insertions in sorted order using SSTables.
5 · Amazon Dynamo
Dynamo is Amazon's key-value store designed for high-volume concurrent updates (each potentially small). Unlike BigTable, it does NOT depend on an underlying distributed file system.

ModelStructured (row+column+timestamp)
Best forBulk reads/writes, analytics

Dynamo
ModelSimple key-value pairs
Best forHigh-concurrency small updates (e-commerce)

Architecture — consistent hashing on a ring

Dynamo uses MD5 to generate a 128-bit hash for each key. The hash space is arranged as a ring. Virtual nodes are mapped onto this ring; each physical server hosts multiple virtual nodes at distributed positions on the ring.

Replication: Each object is replicated to the primary virtual node plus N−1 additional virtual nodes (where N = number of physical nodes). A write to one virtual node is forwarded to all replicas.

Quorum protocol & eventual consistency

OperationQuorum ruleTrade-off
Read (R)Must read from R replicasHigher R = stronger consistency, more overhead
Write (W)Must write to W replicasHigher W = stronger consistency, more overhead
Quorum conditionR + W > NGuarantees at least one node in common — ensures reads see latest write
Eventual consistency: Under high concurrent read/write load, Dynamo guarantees that all replicas will eventually converge to the same value — not necessarily immediately. Vector clocks / version tracking handles conflict resolution.
Implementation: Storage engines used at node level include BerkeleyDB (used by Amazon) and can also use MySQL.
6 · Cloud Data Stores (Google App Engine Datastore / Amazon SimpleDB)
Data stores are simple traditional key-value pair databases offered by cloud providers — Google App Engine Datastore (built on BigTable) and Amazon SimpleDB.

All entities/objects in the datastore reside in one big table. They use column-oriented storage (column families), unlike traditional row-oriented RDBMS.

Key features

Sharding
Horizontal partitioning
BigTable is horizontally sharded across disks. Data stored lexicographically by key — enables efficient prefix and range queries. Queries never need to scan the whole dataset.
Indexes
Multiple index tables
Multiple index tables support varied query types. Query execution automatically picks the index with highest selectivity. Automatically creates single-property indexes and kind indexes for efficient lookups.
Transactions
Entity groups
Entities that are frequently accessed together are grouped for transactional purposes — reduces cross-shard transaction overhead.
Query types
Prefix + range queries
Lexicographic key ordering enables both prefix queries (all keys starting with X) and range queries (all keys between A and B) efficiently.
Summary
Row vs Column: Row-oriented storage is optimal for transactional workloads; column-oriented is optimal for analytics and data warehouses.
Parallel DB Architectures: Shared memory (tight coupling, limited scale) → Shared disk (moderate coupling) → Shared nothing (fully independent, max scale — standard for cloud).
GFS / HDFS: Large files split into replicated chunks (3×) across commodity servers. Master manages metadata only. Fault tolerance via heartbeats and automatic primary reassignment.
BigTable: Structured storage on GFS. Access by row key + column key + timestamp. Column families. Tables split into tablets managed by tablet servers.
Dynamo: Key-value store with consistent hashing ring, virtual nodes, replication. Eventual consistency via quorum protocol (R + W > N).
Cloud Data Stores: Key-value, column-oriented, sharded, lexicographic key ordering, multiple index tables for query efficiency.
