Lecture 41 HIGH priority

Cloud–Fog Computing: Overview

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Introduces the cloud-fog-edge computing paradigm in depth — why cloud latency limits real-time applications, how fog nodes process data at the network edge, the layered cloud-fog-edge architecture, and a health domain case study with performance comparisons. Core architectural concepts with quantitative performance motivation; expect exam questions on fog vs. cloud properties and the three-tier paradigm.

1 · Cloud Limitations that Motivate Fog
Core problem: Cloud is a centralized infrastructure. All data must travel over the network to the cloud, be processed, and results sent back. For high-frequency IoT sensor data and real-time applications, this round-trip latency is prohibitive.
Limitation
High Latency
Network delay from edge device to distant data center and back is significant. Cloud is not designed as a High Performance Computing (HPC) platform — latency is architecturally high.
Limitation
Bandwidth Burden
Large volumes of IoT-generated data (the 3Vs: Volume, Variety, Velocity of big data) create enormous bandwidth requirements when all raw data is sent to the cloud.
Limitation
Not Designed for IoT Scale
Cloud infrastructure was not originally designed for the volume, variety, and velocity of IoT data streams or the interoperability challenges across heterogeneous sensing devices.
IoT/Edge Limitation
Insufficient Edge Resources
Edge sensing devices (pulse oximeters, temperature sensors) have minimal compute, minimal storage, and limited power — they cannot perform sophisticated analytics locally.
2 · Fog Computing — Concept
Fog computing: A model in which data processing and applications are concentrated in devices at the network edge rather than almost entirely on the cloud. Term coined by Cisco to ease wireless data transfer to distributed devices in IoT paradigms.

Analogy: Cloud is up in the sky; fog is near the surface. Fog brings intelligence down from the cloud closer to the devices that generate and consume data.

Key idea

Network infrastructure devices — routers, Wi-Fi gateways, cellular base stations — often have surplus compute resources unused during data forwarding. Fog repurposes these (or dedicated fog nodes) to execute application logic at the network edge, reducing traffic that must reach the cloud.

Temperature control example: 40 sensors across 4 studios on a floor each sending temperature to the cloud is wasteful if the only decision is "within range / out of range." A fog node at the floor's gateway can make that local decision and only transmit an alert when out-of-range — drastically reducing cloud-bound traffic.
What fog achieves: (1) Lower latency for local decisions. (2) Reduced cloud-bound bandwidth — only processed/summary data forwarded. (3) Better support for real-time applications. (4) Inherent location-awareness (fog nodes know their coordinates).

Fog is NOT a replacement for cloud. Fog lacks global view and large-scale resources. It is a complementary layer — local decisions happen at fog; global analytics and provisioning happen at cloud. The combination gives the best of both.
4 · Cloud–Fog–Edge Layered Architecture
Cloud (Level 0) Global analytics, large-scale storage, provisioning, cross-regional decisions — receives processed/summary data from fog
ISP Layer (Level 1) Internet Service Provider infrastructure between fog and cloud
Area Gateway / Fog Nodes (Level 2) Intermediate processing layer; performs local analytics, filtering, aggregation; transmits only relevant/processed data to cloud
Mobile Devices (Level 3) Collect data from sensors, perform basic preprocessing; may also act as lightweight fog nodes
Edge/Sensing Devices (Level 4) IoT sensors, body area networks — data capture; minimal compute; may do basic noise filtering before transmitting
Edge vs. Fog: In some literature, "edge" and "fog" are used interchangeably. In this paradigm: edge = sensing devices closest to the physical world; fog = intermediate processing layer between edge and cloud.

6 · Fog Computing Challenges
Challenge
Interoperability
Fog nodes may be heterogeneous (routers, mobile devices, dedicated gateways) — they must agree on protocols for data format and transfer to cloud.
Challenge
Timing Coordination
Different fog nodes send data at different rates — synchronization and timing relationships between nodes must be managed.
Challenge
Management Complexity
Adding an intermediate layer between IoT and cloud increases overall system management complexity — resource allocation, monitoring, fault handling all multiply.
Challenge
Performance Guarantee
Whether the fog deployment delivers net gains depends on the specific application — not all use cases benefit equally; analysis required before deployment.
Summary
Fog Computing: Data processing at the network edge (routers, gateways, mobile devices) rather than the distant cloud. Coined by Cisco to address IoT data volume and latency constraints.
Key benefit: Fog reduces cloud-bound bandwidth, lowers response latency, and enables real-time local decisions — while cloud still provides global analytics and large-scale resources.
Not a replacement: Fog has no global view and limited resources. It is complementary to cloud — local decisions at fog, global decisions at cloud.
Challenges: Heterogeneous fog nodes create interoperability complexity; timing coordination and management overhead increase with the intermediate layer.
Architecture: Three-tier paradigm — Edge (sensors) → Fog (area gateways, routers) → Cloud (global analytics). Communication is bidirectional at each tier.
