Lecture 10 High priority

Web Services, Service Oriented Architecture

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Covers web services and service oriented architecture (SOA), a major building block of cloud computing: definitions, history, the publish-find-bind model, and the core components SOAP, WSDL and UDDI built on XML. Concept-heavy and foundational; it ties the XML lectures to how IaaS, PaaS and SaaS services are offered and discovered.

1 · What Are Web Services?
There are several definitions in the literature:
SourceDefinition
W3C (Oct 2002)A software application identified by a URI, whose interfaces and bindings can be defined, described and discovered as XML artifacts
MicrosoftProgrammable application logic accessible using standard Internet protocols
IBMAn interface that describes a collection of operations that are network accessible through standardized XML messaging
SunSoftware components that can be spontaneously discovered, combined and recombined to provide a solution to the user's problem or request
Key insight: web services are an XML based phenomenon. Services are available at a standardized URI and work on an XML based message exchange protocol. Applications can talk to each other without caring what happens in the background; only where the service is and how to talk to it matters. Legacy applications can also talk to other applications. Unlike tightly bound client-server protocols, this is loosely bound.

All of these facilitated the evolution of web services.

Distributed computing

For substantial applications it is often more efficient, or even necessary, to run different tasks on different computers: N-tier applications. A 3-tier application might have the user interface on one computer, business-logic processing on a second and a database on a third. Components (e.g. programming objects) on different computers must communicate, e.g. via DCE, CORBA, DCOM or RMI. Interoperability (communicating and sharing data with software from different vendors and platforms) is a major issue and is limited among conventional proprietary distributed computing technologies.

Electronic Data Interchange (EDI)

EDI is computer-to-computer exchange of business data and documents between companies using standard formats recognized nationally and internationally. The information is organized according to a format set by both participating companies, so the format or schema must be known before data is exchanged and the other party knows what data to expect.
Lower operating costs (saves time and money) Less errors, more accuracy (no data entry) Increased productivity (faster throughput) Faster trading cycle (streamlined processes)
3 · Web Services: Features
Web services take advantage of OOP by letting developers build applications from existing software components in a modular approach, transforming a network such as the Internet into one library of programmatic components, with significant productivity gains. They improve distributed computing interoperability using open (non-proprietary) standards that can enable, theoretically, any two software components to communicate. They are also easier to debug because the communication protocols are text-based rather than binary.
Example (online travel booking): a travel portal has neither flights nor hotels itself. It talks to different airline services, pulls the data and shows it to the user; when booking, it calls credit card, debit card or net banking services. Multiple services are amalgamated in a choreographed way to execute one job. The airlines are not directly hooked to the user, and the card provider need not know a ticket is being bought; each service acknowledges a request in a particular form and replies in a particular form, an XML type of message exchange.

Web services vs EDI and WWW

Web services vs EDI

4 · Three Problems Web Services Solve
Interoperability
Lack of interoperability standards in distributed object messaging: DCOM apps are strictly bound to the Windows operating system, and RMI is bound to the Java language.
Firewall traversal
CORBA and DCOM use non-standard ports. Web services use HTTP, and most firewalls allow port 80, leading to easier and dynamic collaboration.
Complexity
A developer-friendly service system using open, text-based standards (like XML) so components in different languages and platforms can communicate.
Incremental adoption: web services can be implemented incrementally rather than all at once, which lessens cost and reduces organizational disruption from an abrupt technology switch. An organization can also keep running legacy software and tools if they have a proper web service interface for the external world.
5 · Web Service Definition Revisited
A web service is an application component that:
CapabilityTechnology
Communicates via open protocolsHTTP, SMTP etc. (any TCP/IP application layer protocol)
Processes XML messages framed usingSOAP
Describes its messages (data organization) usingXML Schema
Provides an endpoint description (where launched, how configured) usingWSDL
Can be discovered (published and discovered) usingUDDI
Key insight: the three major components are SOAP, WSDL and UDDI, all W3C compliant and based on XML.

6 · Service Oriented Architecture (SOA)
SOA is IBM's model for web service interactions, consisting of relationships between three entities. It is a generic model describing service collaboration, not specific to web services only.
Service provider
Owner of the service and the platform that hosts access to it.
Service requestor
The consumer: a business that requires certain functions, or an application looking for and invoking an interaction with a service.
Service registry (broker)
A searchable registry of service descriptions where providers publish their service descriptions.

Web service model

▶ 18:13
Worth watching: the triangle of service registry, service provider and service requestor with Publish, Find and Bind arrows (WSDL and UDDI on the publish and find sides).
The requestor needs a way to find where services are, so there is a registry. The provider publishes a new or updated service in the registry, the requestor finds the service from it using WSDL and UDDI, and then binds with the provider (possibly choosing among more than one provider). Anything developed on this basis is a service driven or service oriented architecture.
Analogy: a telephone directory (yellow and white pages). The directory tells you how to search, e.g. for a plumber, so it acts as a directory or registry service.
OperationMeaning
PublishService descriptions are published so the requestor can find them
FindThe requestor retrieves a service description directly or queries the registry for the service required
BindThe requestor invokes or initiates an interaction with the service at runtime

8 · XML Recap and XML vs HTML
XML developed from SGML (Standard Generalized Markup Method) and is widely supported by W3C. Its essential characteristic is the separation of content from presentation; it is designed to describe data. An XML document can optionally reference a DTD (schema; XSD is more popular), the parser checks syntax, and if the document adheres to the schema it is valid. Tags are not predefined, so you define your own, which enables cross-platform data communication in web services.

9 · SOAP
SOAP (Simple Object Access Protocol) is a format for sending messages over the Internet between programs. It is XML-based, W3C compliant, platform and language independent, simple and extensible, and stateless and one-way (though applications can create more complex interaction patterns). It uses mainly HTTP as the transport protocol: the HTTP message contains the SOAP message as its payload section.
Caution: this "transport protocol" (HTTP carrying SOAP) must not be mixed up with the TCP/IP or OSI transport layer protocols.

SOAP building blocks

BlockRequired?Purpose
EnvelopeRequiredIdentifies the XML document as a SOAP message
HeaderOptionalContains header information

FaultOptionalErrors that occurred while processing the message
Message structure: a request invokes a method on a remote object and the response returns the result of running the method. The SOAP specification defines an envelope that wraps the message itself. The message is a different vocabulary, and a namespace prefix is used to distinguish the two parts. The SOAP message becomes the payload of the transport protocol (HTTP).

Why SOAP, characteristics and usage

Other technologies failed on the Internet
Unix RPCRequires binary-compatible Unix implementations at each endpoint
CORBARequires compatible ORBs
RMIRequires Java at each endpoint
DCOMRequires Windows at each endpoint
SOAP: platform-neutral choice
FormatSimply an XML wire format
RestrictionsNone on the endpoint implementation technology, so legacy things can run
Extensibility
Security and WS-routing are among the extensions under development.
Neutrality
Can be used over any transport protocol such as HTTP, SMTP or even TCP.
Independence
Allows any programming model.
Usage models: (1) RPC-like message exchange, where the request bundles the method name and parameters and the response contains return values (not required by SOAP). (2) Any kind of body content, e.g. XML documents of any type: send a purchase order document to the inbox of a B2B partner and expect a shipping and exceptions report as the response.
SOAP security: since SOAP uses HTTP it can use HTTP security, mainly HTTP over SSL. But SOAP can also run over other application protocols (such as SMTP), so security has to be considered separately; the WS-Security specification defines a complete encryption system. Details are deferred to the security lectures.
10 · WSDL
WSDL (Web Services Description Language; the slide spells it Definition) is an XML vocabulary standard, W3C compliant, for describing web services and their capabilities. It is the contract between the XML web service and the client. It specifies what a request message must contain and what the response will look like in unambiguous notation, and defines where the service is available and which communications protocol is used to talk to it.
A WSDL document is just a simple XML document. It defines a web service using these major elements:
ElementDescribes
port typeThe operations performed by the web service
messageThe messages used by the web service
typesThe data types used by the web service
bindingThe communication protocols used by the web service

Binding to SOAP: the WSDL description binds the SOAP message, i.e. it describes how the SOAP data is transferred between source and destination (requestor, registry, consumer).
11 · UDDI
UDDI (Universal Description, Discovery and Integration) is a framework to define XML-based registries. Registries are repositories that contain documents describing business data and also provide search capabilities and programmatic access to remote applications. Businesses can publish information about themselves and the services they offer, and requestors look up this metadata and how to bind with a provider.

Worth watching: the UDDI roles triangle (publish, find, bind) and the Harbour Metals example showing the registration and discovery steps.
Service registry
Supports publishing and locating services, like telephone yellow pages.
Service provider
Provides e-business services and publishes them through a registry.
Service requestor
Finds required services via the service broker and binds to services via the service provider.
Example (Harbour Metals): Harbour Metals creates an online website with a local ASP; the ASP registers Harbour Metals with the UBR (UDDI registry); marketplaces and search engines query the UBR, cache Harbour Metals data and bind to its services; consumers and businesses then discover Harbour Metals and do business with it.

12 · Security, QoS and Relevance to Cloud
Security is an integral part of web services and works as a vertical across the stack, with components such as web service policy, trust, privacy, secure conversation, federation and authorization. Management and QoS also work vertically. These are covered in later lectures.
Why it matters for cloud: web services and SOA play an important role in setting up the cloud. For IaaS, PaaS, SaaS or any XaaS, the basic building block is the web service: the publish, find and bind phenomenon also holds for cloud services, where one must know the service provider and consumer and where the service is launched. The development of web services and SOA played an important role in making cloud computing viable.
Summary
Web services: software applications identified by a URI, whose interfaces and bindings can be defined, described and discovered using XML; loosely coupled, standards based and platform independent.
Why they exist: they solve interoperability, firewall traversal (HTTP on port 80) and complexity, and can be adopted incrementally while legacy software keeps running.
Versus EDI: similar capability but simpler, cheaper and needing no predefined data format agreement; unlike the WWW, visual and non-visual components are separate.
SOA: three entities (service provider, requestor and registry or broker) with three operations: publish, find and bind.
Components: XML (data representation), SOAP (messaging), WSDL (service description) and UDDI (registry), with security, management and QoS spanning the stack.
Steps of operation: the client queries the UDDI registry, gets the WSDL, then exchanges SOAP request and response messages with the web service.
SOAP: XML-based, stateless, one-way messages with an envelope, optional header, required body and optional fault, carried as the payload of HTTP; platform neutral where Unix RPC, CORBA, RMI and DCOM were not.
WSDL and UDDI: WSDL is the contract (port type, message, types, binding) between service and client; UDDI is the XML registry, like telephone yellow pages.
Example: an online travel portal choreographs airline and payment services without the user connecting to them directly.
Caveat: SOAP can run over protocols other than HTTP (such as SMTP), so HTTP security alone is not enough; WS-Security defines a complete encryption system.
