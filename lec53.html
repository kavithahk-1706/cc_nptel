Serverless Computing — II

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Dives into the three dominant serverless platforms — AWS Lambda, Google Cloud Functions, and Microsoft Azure Functions. Covers the key concepts, components, event triggers, and billing model of each. Useful for platform-specific exam questions; the core serverless theory is in Lecture 52.

3 · AWS Lambda
AWS Lambda: An event-driven serverless computing platform provided by Amazon as part of AWS. Developers upload code in any supported language; Lambda handles execution. No need to provision, launch, or manage AWS resources — put code on Lambda and it runs. Billed only when Lambda executes code — never for idle time.

Lambda Components

Component
Function
A program or script that runs in AWS Lambda. Lambda passes invocation events into the function; the function processes the event and returns a response. The developer uploads and maintains only this function code.
Component
Runtime
Allows functions in various languages (Java, Python, Go, C#, others) to run on the same base execution environment. Configures functions to match the selected programming language — the developer picks the language; Lambda picks the runtime.
Component
Event Source
An AWS service (SNS, S3, API Gateway, DynamoDB, etc.) or custom service that triggers Lambda function execution. Lambda code is executed in response to events from these services — e.g., file added/deleted in S3, HTTP request from Amazon API Gateway.
Component
Lambda Layers
A distribution mechanism for libraries, custom runtimes, and other function dependencies. Layers allow shared code to be packaged separately from the function, keeping function packages small and reusing dependencies across functions.
Log stream: Developers annotate function code with custom logging statements. The log stream lets you analyze execution flow and performance of AWS Lambda functions — useful for debugging without access to underlying infrastructure.
4 · Google Cloud Functions
Google Cloud Functions: A serverless execution environment for building and connecting cloud services. Developers write simple, single-purpose functions attached to events emitted from Google Cloud infrastructure and services. Code executes in a fully managed environment — no provisioning or server management required.

Core Concepts

Concept
Events
Occur in cloud platform services — e.g., file uploaded to Cloud Storage, message published in Pub/Sub, direct HTTP invocation, new object in a bucket, metadata updated. Multiple event occurrences → multiple function invocations, handled automatically by Cloud Functions infrastructure.
Concept
Triggers
The event plus associated metadata. A Cloud Function is configured to be triggered by a specific event type. When the event fires, the trigger is activated and the cloud function is invoked. The function can be configured to respond to one event type or multiple.
Concept
Event Data
Data passed to the Cloud Function when a trigger fires. The function uses this data to determine what caused the event (source, metadata) and performs the appropriate processing. The function can also call external APIs and write back to cloud services as part of its execution.
Concept
Stateless Execution
Functions model their execution in a stateless fashion. State must be maintained outside the Cloud Functions framework — e.g., in a cache like Memcached, or in a database like Cloud Firestore. The function itself does not persist state between invocations.

5 · Microsoft Azure Functions
Azure Functions: A serverless solution that allows developers to write less code, maintain less infrastructure, and save on cost. Same fundamental philosophy as Lambda and Cloud Functions — focus on code; Azure handles the rest. A function in Azure consists of two parts: (1) the code in a supported language, and (2) configuration stored in function.json.
Config generation: For compiled languages (C#, Java), the function.json configuration is auto-generated from annotations in the code. For scripting languages (JavaScript, Python), the developer must provide the configuration file manually.

Azure Functions Key Features

Feature
Language Support
Supports C#, Java, JavaScript, Python, and others. Custom handlers allow using virtually any other language — the developer uses their preferred language without platform lock-in.
Feature
Flexible Pricing
Consumption plan: pay only when functions are running (same pay-per-execution model as Lambda and Cloud Functions). Premium and App Service plans offer features for specialized needs with more predictable pricing for high-throughput workloads.
Feature
Automated Deployment
Large range of deployment options: tool-based approach or external pipelines (CI/CD). Integrates with standard DevOps toolchains for continuous delivery of function updates.
Feature
Monitoring and Testing
Monitor tools and testing strategies provide insight into application execution — useful for troubleshooting without direct server access.

Summary
Serverless focus shift: Cloud computing targets system administrators; serverless targets programmers. The programmer writes only business logic — the provider handles all infrastructure, scaling, and orchestration.
AWS Lambda: Event-driven FaaS by Amazon. Components: Function (code), Runtime (language env), Event Source (AWS services like S3, API Gateway), Lambda Layers (shared libraries), Log Stream (debugging). Charged only on execution.
Google Cloud Functions: Functions triggered by events from cloud services. Core concepts: Events (triggers in cloud services), Triggers (event + config), Event Data (passed to function on invocation), Stateless execution (state stored externally, e.g., Memcached).
Azure Functions: Function = code + function.json config. Compiled languages auto-generate config from annotations; scripting languages require manual config. Consumption plan: pay-per-execution. Supports C#, Java, JavaScript, Python, and custom handlers.
Platform billing — common rule across all three: You are charged only when the function executes. A non-running function costs nothing — unlike IaaS where you pay for provisioned capacity regardless of utilization.
