Introduction to MapReduce

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Introduces MapReduce — Google's parallel programming paradigm for processing massive datasets on thousands of commodity processors. Covers the word-frequency scalability analysis motivating the design, the two-phase Map/Reduce execution model, fault tolerance, and efficiency formula. Highly exam-relevant.

1 · What is MapReduce?
MapReduce is a parallel programming model developed at Google, designed to process and generate large volumes of data via massively parallel computation on tens of thousands of processors.

Origins and motivation

Original purpose
Large-scale web search
Built to process Google's massive corpus of web documents stored in GFS and BigTable. Primary task: text processing and indexing at internet scale.
Now
General scientific computing
Adopted widely for scientific data processing. Open-source implementation: Hadoop (originally developed at Yahoo, now available as pre-packaged AMIs on Amazon EC2).

Core design goals

Fault tolerant Inherently parallel workloads Works on GFS/HDFS/BigTable Scalable to thousands of processors
Prerequisite: MapReduce only works when the problem has inherent parallelism. A strictly sequential chain of operations gains nothing from parallel execution.
2 · Parallel Efficiency — Motivation

Ideal parallel speedup: a task taking time T on one processor takes T/p on p processors. In reality, three factors reduce efficiency:

Synchronization
Processors must coordinate on shared state and timing. Coordination overhead grows with processor count.
Communication
Inter-processor messaging costs real time. Passing partial results between nodes is not free.
Load imbalance
Work may not divide evenly — some processors finish early and sit idle while others are still running.
Parallel efficiency formula:
η = T / (p · Tp)
where T = single-processor time, Tp = parallel execution time with p processors.

Scalable: efficiency remains constant as data size n and processor count p both increase proportionally.
Also: for fixed p, efficiency increases as n grows (more data per processor = less relative overhead).
3 · Case Study — Word Frequency Counting
Problem: Given a huge collection of n documents and m distinct words, compute the frequency (total occurrence count) of each word across the entire collection. This is a classic search-engine indexing problem.

Two parallelization strategies exist. Assume p processors, each word occurs on average f times, and cost c = time to read one word = time to send one word via inter-processor communication.

Approach 1 — Partition by words (m/p words per processor)

Strategy: Each processor is responsible for m/p words. It reads all n documents and counts occurrences of its assigned words.

Problem: Each processor reads the entire document set (n × m × f) but only contributes useful work for m/p words. Most reads are wasted — the processor reads words it was not assigned to count.

Parallel efficiency: η ≈ 1/p — efficiency falls as p increases. Not scalable.

Approach 2 — Partition by documents (n/p documents per processor)

Strategy: Each processor handles n/p documents and counts all m words within its partition. Partial frequency vectors from all processors are aggregated at the end.

Key insight: Every disk read is useful — every word read contributes to the final count. No wasted I/O.

Parallel efficiency: η ≈ 1 / (1 + 2/(p·n·f)) → approaches 1 as n·f grows for fixed p.

Scalable: if both n (data) and p (processors) increase proportionally, efficiency stays constant. Also, for fixed p, efficiency increases as n grows.

Lesson for MapReduce: Approach 2 — partition the data, each processor works on all words but a subset of documents, then aggregate — is the model MapReduce follows.
4 · MapReduce Programming Model
MapReduce is a parallel programming abstraction with two phases — Map and Reduce — coordinated by a master process. Configurable number of M mapper processors and R reducer processors.

Map phase

Input read Each mapper reads approximately 1/M of the total input data from global GFS/HDFS storage
Map operation Transforms input key-value pairs → intermediate key-value pairs: map(k₁, v₁) → [(k₂, v₂)]
Output to local disk Each mapper writes one output file PER reducer, sorted by key, to its local disk. Master tracks all file locations.

Reduce phase

Locate input Master informs each reducer where (which mapper local disks) its input files are stored
Fetch via RPC Reducer makes Remote Procedure Calls to each mapper to fetch its designated output file
Reduce operation Groups all values with the same key, applies aggregate function f: (k₂, [v₂]) → (k₂, f([v₂]))
Final output Results written back to GFS/HDFS
Key structural point: Every mapper produces exactly R output files — one per reducer. The master knows where all of them live. Reducers fetch their slice from every mapper's local disk via RPC.

6 · Fault Tolerance in MapReduce
Detection
Heartbeat messages
Master sends regular "are you alive?" probes. If a node communicates but shows no progress, master duplicates its task and assigns it to a free or already-finished processor.
Mapper failure
Full re-execution
Master reassigns all key-value pairs from the failed mapper to another worker node. The failed mapper's local output files are lost and must be regenerated.
Reducer failure
Partial re-execution
Only the remaining (not yet completed) reduce tasks are reassigned. Tasks already completed have results written to GFS — those don't need rerunning.
Straggler handling
Speculative execution
If a node is alive but slow, master assigns the same task to another processor in parallel. Whichever finishes first wins.
Why mapper failure is more expensive: Mapper output lives on the mapper's local disk. If the mapper dies, that output is gone. Reducer output goes to GFS and survives reducer failure.
7 · MapReduce Parallel Efficiency

Let: w = computation time per word, c = time to read/write one word from/to disk, D = total data volume, P = processors (acting as both mappers and reducers).

StageTime per processorData produced
Mapc_m · D/P (read) + w · D/P (compute)D′ (intermediate key-value pairs)
Local writeEach mapper writes D′/P to local diskP files (one per reducer)
Remote readEach reducer fetches D′/P from each of P mappers → D′/P²· P = D′/P readsReducer input
Reducec_r · D′/P + function aggregationD″ (final output)
MapReduce parallel efficiency (simplified, ignoring decomposition overhead):

η = 1 / (1 + 2c/w)

Interpretation: If disk I/O cost c is much smaller than computation cost w (c ≪ w), efficiency → 1. Compute-heavy tasks benefit most from MapReduce. I/O-bound tasks with high c/w ratio lose efficiency.
8 · Applications of MapReduce
Primary use
Document indexing
Map emits (word, document_id) pairs. Reduce groups by word and builds an inverted index — the core of Google Search. Also handles structured data indexing.
Database
Relational operations
SQL-style GROUP BY, JOIN, and aggregation on large datasets that would be infeasible in a single RDBMS. Takes advantage of fault-tolerant parallel execution.
Analytics
Word count / frequency analysis
Classic MapReduce example — count occurrences of each term across a large corpus. Directly maps to the word-frequency motivating problem.
Science
Scientific data processing
Genomics, astronomy, physics simulations — any large-scale embarrassingly parallel computation over distributed data.
Summary
MapReduce design: Two-phase parallel paradigm — Map transforms input key-value pairs into intermediate pairs; Reduce aggregates them by key. M mappers, R reducers, one master coordinator.
Scalability insight: Partitioning documents (not words) across processors makes every disk read useful, achieving efficiency → 1 as data grows. This is the design philosophy behind MapReduce.
Mapper output detail: Each mapper writes exactly R files (one per reducer) to its local disk sorted by key. Master tracks all locations. Reducers fetch via RPC.
Fault tolerance asymmetry: Mapper failure requires full re-execution (output on local disk is lost). Reducer failure only requires re-executing incomplete tasks (completed output is in GFS).
Efficiency formula: η = 1/(1 + 2c/w). Compute-heavy tasks (small c/w) benefit most; I/O-heavy tasks are penalized by disk overhead.
