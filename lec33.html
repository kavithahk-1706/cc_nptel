Lecture 33 MED priority

Fog Computing – I

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Introduces fog computing as an extension of cloud toward the network edge — motivation from IoT and real-time applications, the 3-tier architecture (devices → fog → cloud), CISCO's origin of the term, enabling technologies, and security challenges. Core concept lecture for understanding edge vs. cloud processing trade-offs.

1 · Motivation — Limits of Cloud-Only Computing
Core observation: Intermediate network devices and edge nodes are becoming increasingly capable. Instead of transmitting all raw data to the cloud, processing can be pushed toward the network edge — reducing bandwidth, latency, and cloud load.

Problems with cloud-only computing

Bandwidth
Massive data volumes
IoT, sensor networks, smart devices generate enormous volumes of data. Transmitting everything to the cloud saturates backbone networks — much of this data is redundant or decidable locally.
Latency
Real-time requirements
Applications like accident prevention, smart traffic lights, autonomous vehicles need immediate response. Waiting for round-trip to a distant cloud datacenter is unacceptable.
Congestion
Core network overload
Centralized datacenters receiving data from all regions causes core network congestion — especially during exigencies (disasters, mass events) when volume spikes.
Redundancy
Unnecessary transmission
If 10 temperature sensors all read ~20°C, there is no need to send all 10 readings to the cloud. A local sink node can aggregate and send one value (or a yes/no threshold result).
Example (from lecture): A lab with 10 temperature sensors sending raw readings to the cloud for threshold checking is wasteful. The local sink node can compute the average and send a single "in range / out of range" flag — identical outcome, fraction of the bandwidth.
2 · Fog Computing — Definition and Origin
Fog computing (also: fogging, edge computing): A model in which data, processes, and applications are concentrated in devices at the network edge rather than existing almost entirely in the cloud. Computing is pushed from centralized datacenters toward the periphery.
Origin
CISCO coined "fog computing"
Introduced as a new model to ease wireless data transfer to distributed devices in IoT networks. CISCO's vision: run applications directly on network-edge devices (routers, switches, gateways) using open-source Linux + network OS on existing hardware.
Relationship to cloud
Extension, not replacement
Fog does not replace cloud. It offloads appropriate workloads to edge devices. Cloud retains its role for large-scale data mining, ML algorithms, big data analytics. Fog + Cloud together provide better service than either alone.
3 · 3-Tier Fog–Cloud Architecture
Cloud (Top) Massive parallel processing, big data mining, ML algorithms, virtually unlimited storage. Handles global, non-real-time workloads.
Fog Layer (Middle) Intermediate network devices (routers, switches, Wi-Fi gateways, cellular base stations). Real-time data processing, caching, computation offloading, local decision-making.
Edge / End Devices (Bottom) Sensors, smart vehicles, cameras, mobile devices, smart meters. Data capture, basic pre-processing, compression; HCI for users.
Data flow principle: Edge devices capture and pre-process → fog aggregates and handles real-time decisions → cloud receives only aggregated/filtered data for deeper analysis. Each layer processes only what it needs to.
4 · Key Characteristics and Benefits
Latency
Low latency, location awareness
Processing close to the device reduces round-trip time. Enables real-time and streaming applications. Location-aware processing handles regional decisions locally.
Bandwidth
Reduced core network load
Aggregating at fog nodes means only aggregated/essential data reaches the cloud. Lowers bandwidth consumption and core network congestion.
Distribution
Widespread geographic presence
Fog nodes are distributed across regions — closer to users than centralized cloud datacenters. Distinct from cloud in proximity, density of distribution, and support for mobility.
Mobility
Mobility support
Mobile devices changing location change their path through fog nodes. Fog handles re-synchronization and path re-establishment locally, without cloud involvement.
Heterogeneity
Device heterogeneity handling
Different sensor types, different sink nodes, different protocols — fog layer can aggregate into standardized format, hiding heterogeneity from the cloud layer.
Scale
Very large node count
IoT deployments involve billions of devices. Fog inherently scales to this by distributing processing across the edge rather than funneling everything to a central point.
Cloud properties preserved: Fog must retain cloud's core advantages — dynamic scalability, minimal client-side infrastructure management, and metered service. A fog model that compromises these loses the original motivation for cloud adoption.
5 · Enabling Technologies for Fog
Virtualization / Containers
VMs and container services (e.g., Docker) reduce resource management overhead using lightweight virtualization. Containers carry their own dependencies — portable across edge devices without reinstallation.
Service-Oriented Architecture (SOA)
Services provided through communication protocols across loosely coupled components. Three roles: service provider, service consumer, service registry. Enables heterogeneous parties to interoperate at the fog layer.
Software Defined Networking (SDN)
Uses open protocols (e.g., OpenFlow) for globally aware software control at network edges. Decouples control plane from data plane. Enables dynamic, programmable routing — critical for fog traffic management.
6 · Security Challenges in Fog
Dispersion problem: Cloud centralizes security enforcement at a few datacenters — easier to harden. Fog distributes processing across many edge devices at different locations — maintaining consistent security protocols across all of them is a serious challenge.
ThreatDescription
Man-in-the-middle attackData processed at distributed edge nodes creates more attack surfaces for interception or tampering compared to centralized cloud
Privacy leakageIntermediate processing at fog nodes may expose private data (location, usage patterns) before it reaches the cloud
Smart meter spoofingIn smart grids, each smart meter/appliance has an IP address. Malicious users can tamper with meters, report false readings, or spoof IP addresses
Mobility trackingFog processing of vehicle data or smart grid consumption can inadvertently reveal individual movement or usage patterns
Standard network attacksAll typical network security issues (DoS, eavesdropping, injection) apply to fog nodes — extended to a much larger, more distributed attack surface
7 · Application Drivers for Fog
Smart grid / smart meters Smart traffic light management Connected / autonomous vehicles Software Defined Networks IoT sensor networks Real-time surveillance / smart cameras Environmental monitoring Disaster response systems
Traffic light example (from lecture): Road cameras detect traffic flow → fog node (local controller) adjusts signal timing dynamically → only aggregated city-level stats go to cloud. Local decision; no cloud round-trip needed for individual light changes.
Summary
Fog computing: Extends cloud to the network edge — data, compute, and applications distributed across fog nodes rather than all in centralized datacenters. Coined by CISCO for IoT contexts.
3-tier model: Edge devices (capture + pre-process) → Fog layer (aggregate, real-time decisions) → Cloud (big data, ML, global analytics).
Key benefits: Low latency, reduced bandwidth, real-time capability, mobility support, heterogeneity handling.
Not a replacement: Fog complements cloud — it offloads latency-sensitive and bandwidth-heavy workloads to the edge; cloud retains global, compute-intensive tasks.
Security caveat: Distributing processing to many edge nodes vastly increases the attack surface. Maintaining security across dispersed fog devices is a major open challenge.
