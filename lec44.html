Lecture 44 HIGH priority

Cloud Federation

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Introduces cloud federation — when and why multiple cloud service providers cooperate to deliver a unified service, the three coupling levels (loosely, partially, tightly), and the four major federation architectures (hybrid/bursting, broker, aggregated, multi-tier). Definition-heavy and architecture-focused; expect exam questions on federation motivations, coupling levels, and the four architectures with their characteristics.

1 · What is Cloud Federation?
Cloud federation (federated cloud): Deployment and management of multiple external and internal cloud services to match a business need. One or more Cloud Service Providers (CSPs) cooperate to deliver an integrated service — transparent to the end customer — that satisfies requirements neither could meet alone.
IIT Kharagpur example: IIT KGP runs an internal private cloud (Meghalwala) inaccessible from outside. During a large-scale exam (2000+ students simultaneously), if internal capacity is insufficient, they federate with an external public cloud to absorb the load — the exam runs seamlessly despite crossing cloud boundaries.

Why Federate? — Motivations

Motivation
Maximize Resource Utilization
One CSP may be resource-constrained while another has surplus. Federation creates a larger resource pool, enabling both to serve more customers at higher utilization.
Motivation
Load Balancing
Distribute load across federated partners — a heavily loaded CSP can shed workload to a lightly loaded partner, improving response times for end users.
Motivation
Expand Service Catalog
A federated CSP can offer services it doesn't host itself by routing to a partner. The collective federation catalog is broader than any individual member's.
Motivation
Expand Footprint and Reliability
Each federated partner effectively gains the geographic and capacity footprint of all members, improving marketability and enabling fault tolerance across geographically separated sites.
2 · Federation Characteristics
Characteristic
Voluntary Participation
Federation is voluntary — no regulatory body mandates which CSPs must federate. Individual CSPs choose partners based on business needs and mutual benefit.
Characteristic
Well-Defined Agreements
Federation requires formal market agreements and SLA terms governing resource sharing, pricing, and obligations among partners. Without this, seamless operation is impossible.
Characteristic
Maximum Geographic Separation
Federation partners should ideally be in different power zones, network zones, and seismic zones. If an environmental disaster affects one partner, the others keep serving the customer base — maximizing reliability.
Characteristic
Enhanced Interoperability
Federation overcomes current cloud limitations — service interruptions, lack of interoperability, degradation — by allowing partner CSPs to handle each other's failures or overloads seamlessly.
3 · Federation Coupling Levels
Loosely Coupled
Limited interoperation between CSPs. Each provider exposes minimal information about its infrastructure. The local CSP has little or no control over remote resources — only basic operations (provision/deprovision VMs). No support for advanced features like cross-site VM migration. Example: private cloud bursting to public cloud with no formal agreement beyond provisioning API.
Partially Coupled
Partners establish a formal contract or framework agreement stating terms and conditions for resource sharing. Contract allows some control over remote resources — e.g., affinity rules for VM co-placement. More monitoring information is exchanged (host energy consumption, VM location). May enable some advanced networking across boundaries. More flexible and efficient than loosely coupled.
Tightly Coupled
Usually governed by the same cloud administrator or all report to a single authority. Advanced control over remote resources — exact VM placement decisions, full monitoring information access. Supports: cross-site networks, cross-site VM migration, high availability techniques across remote cloud instances, virtual storage systems spanning boundaries. Typically within one corporation's multi-site deployments.
4 · Four Federation Architectures

1. Hybrid / Cloud Bursting Architecture

Definition: Combines existing on-premise infrastructure (private cloud) with resources from one or more public clouds to satisfy peak demand. The local cloud is the primary; external clouds absorb overflow during demand spikes.
Property
Coupling
Loosely coupled — local cloud OS has no advanced control over virtual resources deployed in the external cloud beyond what the provider's basic API allows.
Property
Use case
Organizations with predictable baseline load (own private cloud) but unpredictable or seasonal peak demand (exam season, product launches, tax period). Most existing cloud managers support hybrid architecture.

2. Broker Architecture

Definition: An intermediary (broker) has access to multiple cloud infrastructures and manages resource deployment on behalf of users. Users submit requests to the broker, which selects the most suitable cloud based on optimization criteria (cost, performance, energy). The broker may distribute a single service's components across multiple clouds.
Property
Coupling
Loosely coupled (or partially coupled). Public clouds typically do not expose advanced control over deployed virtual resources to third parties.
Property
Use case
Most common federation scenario. Easiest to implement and maintain — broker preserves individual cloud provider privacy while enabling global load balancing and service selection.

3. Aggregated Architecture

Definition: Two or more partner clouds interoperate to aggregate their resources into a single large virtual pool presented to users as one unified infrastructure. Users see a single large virtual cloud; actual resources are distributed across partner sites.
Property
Coupling
Partially coupled — partners must share resource availability information for aggregation decisions. Partners may own their infrastructure independently but agree to cooperate and share resource metadata.
Property
Use case
Multiple organizations or CSPs with separate ownership who agree to pool resources. Aggregation decisions may be pre-arranged rather than fully on-the-fly, due to the constraints of partial coupling.

4. Multi-Tier Architecture

Definition: Two or more cloud sites, usually belonging to the same corporation, each running their own cloud OS and managed by a third, hierarchically superior cloud OS instance. The root cloud OS has full control over all subordinate cloud sites' resources.
Property
Coupling
Tightly coupled — controlled by one administrative authority. Resources at all sites are exposed as if they were in a single cloud. Cross-site VM migration, cross-site networks, and high availability across sites are feasible.
Property
Use case
Large corporations with geographically distributed cloud infrastructure (e.g., data centers in multiple cities). Hierarchical management provides uniform access, advanced management features (HA, load balancing, fault tolerance), and consistent policy enforcement across all sites.

Summary
Cloud Federation: One or more CSPs cooperate to deliver a unified, integrated service — transparent to end users. Motivation: capacity constraints, load balancing, wider service catalog, geographic reach and reliability.
Three coupling levels: Loosely (minimal information sharing, no advanced control), Partially (formal contract, some control and monitoring access), Tightly (same authority, full control, advanced cross-site features).
Four architectures: Hybrid/Bursting (private + public for peak demand, loosely coupled) → Broker (intermediary across multiple clouds, loosely–partially coupled) → Aggregated (pooled resources from partner clouds, partially coupled) → Multi-Tier (hierarchical, same corporation, tightly coupled).
Multi-tier is the only architecture that fully supports advanced features like cross-site VM migration, cross-site virtual networks, and high availability across remote cloud instances — because it requires a single administrative authority.
