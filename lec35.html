Lecture 35 MED priority

Use Case: Geospatial Cloud

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Applies cloud computing principles to the geospatial domain — covering what GIS and spatial data are, why they need cloud infrastructure, the architecture of a geospatial cloud, and the IIT Kharagpur Meghamala experimental deployment. Applied and use-case focused; introduces no new core cloud theory but shows how cloud economics, resource pooling, and web services map onto a real domain with heterogeneous, multi-stakeholder data.

1 · Geospatial Data — Definition and Characteristics
Geospatial data: Information explicitly linked to a location on the earth's surface. Every data item is anchored to a coordinate system (typically lat-long). Over 90% of real-world data is estimated to carry some spatial attribute — student records (hall, department, hometown), product delivery addresses, pollution sensor readings, weather stations, etc.

Static vs Dynamic

Static Spatial Data
Change rateDoes not change or changes over very long periods
ExamplesState/district boundaries, lakes, parks, roads (geometry)
Also calledPseudo-static — building geometry is static even if electricity demand varies
Dynamic Spatial Data
Change rateVaries frequently or continuously over time
ExamplesTraffic movement, city population at any hour, air quality sensors
ImplicationRequires time-stamped storage and continuous update pipelines

Scale Dependency

Geographic data varies with the scale of observation. A building viewed from a satellite is a point; viewed at street level it is a polygon. Scale affects the level of detail, precision, and the nature of spatial relationships — this is a fundamental challenge in multi-source data integration.

Common Geographic Data Categories

Legal/Administrative (boundaries, jurisdictions) Cultural and Climatic Economic Hydrological (rivers, canals) Elevation and Terrain Infrastructure (roads, utilities) Remote sensing (satellite imagery, aerial photos) Sensor data (GPS, pollution, temperature, weather stations)
2 · Geographic Information System (GIS)
GIS: A hardware-software-data-people platform for capturing, storing, querying, analyzing, and displaying geospatial data. The platform handles data where the spatial relationship — location on earth — is the defining attribute.

GIS Components

Hardware
Physical Infrastructure
Storage for large volumes of spatial data; compute for intensive spatial operations; network for distributed data access.
Software
GIS Platforms and Tools
Spatial database engines (PostGIS, Oracle Spatial), analysis tools, map rendering, web service interfaces (OGC WMS/WFS standards).
Data
Spatial Datasets
Maintained by different organizations with proprietary ownership. Heterogeneous in format, reference system, scale, and semantics. Volume is enormous.
People
Specialized Expertise
GIS requires a special category of staff who understand coordinate systems, spatial analysis algorithms, data semantics, and domain knowledge. Scarce and expensive.

Why GIS is Computationally Intensive

Spatial Operations
Shortest Path and Overlay
A road network represented as a graph over a country can have millions of edges. Shortest-path algorithms and spatial overlay operations (buffering, intersection) are computationally expensive.
Variable Load
Dynamic Scaling Needed
GIS queries arrive sporadically. The GIS server must scale up during peak query periods and release resources when idle — exactly the use case cloud elasticity is designed for.
Data Volume
Massive Storage Requirements
Satellite imagery, elevation data, and sensor streams generate enormous volumes. Moving this data is extremely difficult — it is more feasible to bring compute to the data than data to the compute.
Network Intensity
Distributed Web Services
Data is maintained by multiple organizations. Spatial web services must federate queries across distributed repositories over the network — high bandwidth, low-latency connectivity is essential.
3 · Spatial Data Infrastructure (SDI)
SDI concept: Treat spatial data as infrastructure rather than as privately held assets. Just as telecom is a utility that anyone hooks into with a SIM card, SDI provides a coordinated framework that any authorized organization can query — regardless of which organization holds the data.
Analogy from lecture: A telecom infrastructure gives you voice, data, and multimedia via a SIM card and plan — you don't own cables or towers. SDI works similarly: you hook into the infrastructure to get spatial data services without storing or managing the underlying datasets yourself.

Why SDI is Needed

Policy Shift
From Project to Societal Mode
Historically, spatial data was collected in project silos. The trend is toward ubiquitous public availability — data collected with taxpayer money should serve society broadly, subject to security/policy constraints.
Integration Requirement
Homogeneity Across Stakeholders
Different organizations store data in different coordinate systems, formats, and scales. Querying across them requires syntactic and semantic homogeneity — a standard encoding and sharing mechanism.
Sustainability
Infrastructure Renewal Cost
GIS hardware depreciates and must be replaced every 3–5 years. Organizations specializing in spatial data collection — not IT — struggle to sustainably maintain infrastructure. Cloud relieves this burden.
Service Model
End Users Want Services, Not Data
A user wants "shortest path from IIT Kharagpur to Kolkata" — not the raw road network database. Service-oriented access (WMS/WFS/WPS over the web) abstracts away data management entirely.
4 · Geospatial Cloud Architecture

The geospatial cloud architecture maps standard cloud actors onto the spatial domain:

ActorRole in Geospatial Cloud
Service Consumer / UserIssues spatial queries (shortest path, buffer, overlay) without knowing where data is stored
Broker / NegotiatorMediates between consumer and multiple data providers; the same spatial dataset may exist in multiple repositories — the broker routes or aggregates
Data CentersHost VMs on which different organizations deploy their spatial datasets and services
SLA ManagerMonitors whether query response times, data quality, and uptime commitments are met
Security AuditorEnforces access policies — data ownership is sensitive (taxpayer-funded survey data, proprietary imagery); auditor ensures only authorized access

Interface GIS

Interface GIS: A middle-tier component that has no data per se — it acts as a gateway connecting consumers to different spatial service providers. It handles resource allocation, data manipulation, and interface services — analogous to a cloud service broker specialized for spatial queries.

5 · Geospatial Cloud Model
Key Technology
Spatial Web Services
Web services (OGC standards: WMS for map rendering, WFS for feature data, WPS for processing) are the interface layer. Services can be inside or outside the cloud; the PaaS model makes load balancing and scaling transparent to the consumer.
Data Integration
Unified Format Requirement
Heterogeneous back-end data sources must be integrated into a unified format (common coordinate reference system, encoding standard) before they can be queried together. The cloud provides the coordination layer for this.
Service Model
PaaS for Spatial Processing
Running spatial services via PaaS makes resource scaling transparent — the consumer does not manage VMs. Load balancing across multiple data centers handles variable query loads automatically.
Data Sources
Multiple Stakeholders
National agencies (Survey of India), state/district bodies, private organizations, and remote sensing data providers all contribute. Each may have different access policies, formats, and reference systems.
6 · IIT Kharagpur Experiment — Meghamala Cloud
Meghamala: IIT Kharagpur's in-house private cloud running OpenStack (open-source cloud platform). Used as an experimental geospatial cloud to demonstrate multi-VM, multi-source spatial query integration.
▶ 27:01
Worth watching: Screenshots from the Meghamala experiment showing Bankura district (West Bengal) road and water network data running in two separate VMs, and the result of on-the-fly integration (merged road network, shortest path, buffered flood zone).

Experiment 1 — Road Network Integration

Data sources: National highway data (National Highway Authority) in one VM; local/state road network (district authority) in another VM — two separate cloud instances.

Operation: On-the-fly merging of the two road networks, then executing a shortest-path query on the combined graph. The consumer supplies only source and destination locations — no awareness of which VM holds which data.

Key insight: Two separate data repositories, maintained by different authorities with different data collection mandates, are integrated as a service — not by physically merging databases, but by pulling on-demand via web services running in separate VMs.

Experiment 2 — Water Network and Flood Vulnerability

Data sources: Canal data (one VM) + river data (another VM), same Bankura district.

Operation: Merge water networks → apply a 500-metre buffer around the merged network → identify the vulnerable zone (population, agricultural land within the buffer) under a heavy-rain/flooding scenario.

Business rule realized: "Areas within 500m of any water body are flood-vulnerable" — computed entirely through service calls without the consumer ever accessing the raw datasets.
7 · Challenges in Geospatial Cloud
Challenge CategoryDescriptionSpatial-Specific?
Spatial Database ImplementationRequires deep understanding of data semantics, spatial indexing (R-trees, quad-trees), and geometry operations. Not a drop-in replacement for standard relational databases.Yes
Scaling Spatial DatabasesSpatial queries (overlay, buffer, path) do not parallelize as naturally as simple key-value lookups. Distributed spatial query execution is an open research problem.Yes
Multi-TenancyMultiple organizations storing data on shared infrastructure with different access policies — who can query whose data, at what resolution, under what SLA.Shared with general cloud
Data-Level InteroperabilityDifferent coordinate reference systems, scales, and encodings must be reconciled before two datasets can be overlaid or joined spatially.Yes
Service-Level InteroperabilitySpatial web services from different providers must be composable — one service's output must be a valid input to another, without format translation overhead.Yes
Security-Level InteroperabilityDifferent datasets carry different access policies. When combining two datasets, the resulting merged product's security classification is not trivially derived from its components'.Yes
Geographically Distributed BackupsSpatial data often covers a specific geography — backup strategy must account for data sovereignty rules (some countries prohibit certain geospatial data from leaving national jurisdiction).Yes
Lack of Complete ControlMoving data to cloud means the owner no longer has full control of data, application deployment, and security enforcement — a known general cloud risk, heightened for sensitive geographic intelligence.Shared with general cloud
Interoperability is the dominant challenge: Unlike relational data where formats are standardized (SQL), spatial data has legacy heterogeneity across coordinate systems (WGS84, UTM, local datums), encoding formats (Shapefile, GeoJSON, KML, GML), and semantics (what counts as a "road" varies by dataset).
8 · Why Cloud Works for Geospatial
Resource Sharing
Shared Resource Pooling
Query load is bursty — disaster events, development planning cycles, elections cause spikes. Cloud elasticity scales up for spikes and releases resources during quiet periods, matching the variable demand profile of GIS workloads.
Cost
Reduced Infrastructure Burden
Organizations collecting spatial data often lack IT infrastructure expertise. Cloud removes the need for them to own, maintain, and refresh (every 3–5 years) hardware — they pay only for what they use.
Data Safety
Managed Services Prevent Loss
Spatial data collections represent enormous past investment — surveys, satellite acquisitions, field measurements. Cloud-managed storage with redundancy prevents loss from hardware failures that would be catastrophic to small agencies.
Flexibility
Deployment Model Choice
Organizations can choose private cloud (sensitive national datasets), public cloud (open civic data), or hybrid models — matching data sensitivity to deployment risk.
Security
Leveraging Cloud Security Investment
Security at scale is expensive. Cloud providers invest heavily in security infrastructure that individual GIS organizations cannot replicate — leveraging this is economically rational.
Service Access
Acquire Services as Needed
Organizations can subscribe only to the spatial services relevant to their domain (hydrology agency needs river data and flood analysis services, not road routing). Pay-per-use model for services.
Summary
Geospatial Data: Explicitly location-linked, can be static or dynamic, scale-dependent, and maintained by heterogeneous organizations with proprietary ownership — making integration the central challenge.
Why Cloud Fits GIS: Spatial workloads are computation-intensive, data-intensive, load-variable, and network-intensive — precisely the characteristics that benefit from cloud elasticity, pay-as-you-go economics, and web service federation.
IIT Kharagpur (Meghamala): Demonstrated on-the-fly integration of multi-VM, multi-source spatial datasets — separate road and water repositories queried through service calls to produce merged route/flood-zone results without the consumer accessing raw data.
Key Challenges: Interoperability (data, service, and security levels) is the dominant barrier; spatial databases are not drop-in cloud components; multi-tenancy with heterogeneous access policies adds complexity beyond standard cloud deployments.
SDI Vision: Treating spatial data as public infrastructure — analogous to telecom — that any authorized party can hook into via standardized web services, hosted on a geospatial cloud, for citizen-centric planning and disaster management.
