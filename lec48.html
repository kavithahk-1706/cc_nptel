Lecture 48 HIGH priority

Docker: Overview, Components, and Architecture

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Covers the Docker container platform in depth — the problem it solves (complex multi-environment software deployment), its key benefits, core concepts (image, layer, container, registry), and the client-daemon-registry architecture that underlies every Docker operation. Conceptual foundation before the demo lectures. Reference: Docker in Practice, Ian Miell and Aidan Hopson.

1 · The Problem Docker Solves
Traditional deployment challenge: Deploying software across different environments (development, test, production) required significant manual effort. Each environment had its own OS variant, libraries, and dependencies — shipping code from one to another meant re-engineering configuration.
Traditional / VM Deployment
PipelineInstall → Configure → Maintain separately on each of: dev server, test server, live server
Config managementComplex array of configuration mechanisms per environment
Environment mismatchCode working on Ubuntu may fail on Red Hat; must re-engineer
VM overheadWaiting for VMs to boot; managing guest OS overhead
Specialist requiredEach tool needs trained engineers familiar with its approach
Docker Deployment
PipelineInstall → Configure once in Docker image → docker run on dev, test, and live
Config managementSingle standardized pipeline to one output; no per-environment config
Environment mismatchAs long as Docker runs on the host, the container runs identically
OverheadLightweight — shares host OS kernel; starts almost instantly
PortabilityImage is self-contained; ships from laptop to server to cloud unchanged
Docker philosophy: Build, ship, and run any app anywhere. Everything goes through a common pipeline to a single output that can be used on any target — no need to maintain an array of configuration mechanisms.
2 · Key Benefits of Docker
Portability
Replace VMs in Many Situations
When you only care about the application (not the OS), Docker replaces VMs. Lighter weight, quicker to start up, easier to move around due to layered filesystem. Scriptable — everything can be automated from the command line.
Portability
Package Software with No Dependencies
A Docker image has no external dependency issues. Build your image and be sure it runs on any modern Linux host with Docker installed — regardless of which Linux variant (Ubuntu, Red Hat, CentOS, etc.).
Developer Productivity
Rapid Prototyping Sandbox
Spin up a sandbox environment almost instantly without disrupting your existing setup or provisioning a full VM. Before Docker, setting up the prototype environment alone consumed significant time.
Developer Productivity
Full-Stack Offline Productivity
Bundle all components of a system into Docker containers and orchestrate them locally on a laptop. Enables working on the full stack even in offline mode — for development and testing without network access.
Operations
Enable Microservice Architecture
Facilitates decomposition of complex systems into a series of composable parts — each manageable, pluggable, and independently deployable. Docker makes each microservice a self-contained unit that reasons in isolation.
Operations
Enable Continuous Delivery (CD)
CD is a software delivery paradigm where every change triggers a rebuild → automated delivery to production. Docker builds are more reproducible and replicable than traditional methods — making CD pipelines far easier to implement.
Quality
Reduce Debugging Overhead
State debugging steps clearly — even in script form — for a system with known properties. Bug reproduction is simpler because the container environment is reproducible. Eliminates "works on my machine" class of bugs.
Quality
Document Software Dependencies
Building a Docker image forces explicit documentation of all software dependencies from the starting point. Since the image must be portable, you cannot skip a dependency — they must all be stated and packaged.
3 · Docker Core Concepts
Concept
Layer
A collection of changes to files — the difference between one version of the application and another. Layers are stored on disk. Each image is built up from multiple layers stacked on top of one another (e.g., OS layer → application v1 layer → application v2 layer).
Concept
Image
A collection of filesystem layers plus metadata. The static, read-only blueprint for a container. Multiple versions of an application can coexist as separate images. Images are pulled from a registry and stored on disk — they are not running processes.
Concept
Container
A running instance of an image. Multiple containers can run from the same image simultaneously (e.g., myapp-container-v1.2, myapp-container-v1.3). When a new version is needed, build a new image (v3) and deploy it as new containers.
Concept
Registry
A catalog/namespace where Docker images are stored and versioned. Can be a private registry (on internal network, restricted access) or a public registry such as Docker Hub (maintained by Docker Inc., internet-accessible). Daemons pull images from registries.

5 · Docker Architecture
Two-part host architecture: Docker on a host machine is split into two parts — (1) the Docker daemon (server-side, with a RESTful API) and (2) the Docker client (command-line tool that talks to the daemon). Communication between the two uses the HTTP protocol.

Components

Docker Client
The command-line program the user invokes. Sends HTTP requests to the Docker daemon and receives responses. Acts as the intermediary between the user (or application) and the RESTful API. Does not manage containers directly — it instructs the daemon.
Docker Daemon
The server process on the host machine. Receives requests from the client via HTTP and returns responses. Responsible for managing images and containers behind the scenes — pulls images from registries, creates and runs containers, manages their lifecycle.
Docker Registry
A service that stores Docker images. A private registry sits on the internal network with controlled access. Docker Hub is the public registry run by Docker Inc., accessible over the internet. Other public registries can also exist.

How It All Works Together

Request flow:
1. User invokes Docker client → client sends HTTP request to Docker daemon on host machine
2. Docker daemon receives request → manages image/container operations behind the scenes
3. If an image is needed, daemon sends HTTP request to private registry (internal network) or Docker Hub (internet)
4. Registry returns the image → daemon returns response to client
Transport protocol note: The HTTP protocol used between client and daemon is the application-layer transport — do not confuse this with the Transport layer of the network stack (TCP/UDP). Docker piggybacks on HTTP for its REST API communication.
Summary
Core philosophy: Build, ship, run any app anywhere. Docker packages code + all dependencies into a self-contained image that runs identically on any host with Docker — eliminating environment-specific configuration problems.
Key advantage over VMs: Docker containers are lighter (no guest OS), faster to start, easier to move, and scriptable — making them preferable when only the application (not the OS) matters.
Image → Layer → Container: An image is a stack of filesystem layers (each layer = set of file changes). A container is a running instance of an image. Multiple containers can run from the same image simultaneously.
Registry: Where images are stored — either a private registry on the internal network (restricted access) or Docker Hub (public, internet-accessible, run by Docker Inc.).
Architecture: Docker client sends HTTP requests to the Docker daemon (RESTful API). The daemon manages all container and image operations, pulling images from registries as needed. The client is just the user-facing intermediary.
CD enablement: Docker's reproducibility makes Continuous Delivery (rebuild on every change → automated delivery to production) far more practical than traditional build methods.
