Lecture 47 HIGH priority

Containers, Kubernetes, and Docker

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Introduces container-based virtualization — a lightweight alternative to full VM virtualization that packages application code with all its dependencies into a portable, isolated unit. Covers why containers emerged, their key advantages, the three deployment eras (traditional → VM → container), and provides an overview of the two dominant open-source implementations: Kubernetes (orchestration) and Docker (container runtime). Foundation for the hands-on demos in subsequent lectures.

1 · What is a Container?
Container: A lightweight virtualization technique that packages application code together with all its dependencies (specific language runtime versions, libraries, settings) into a self-contained unit. The application runs quickly and reliably across any computing environment — laptop, VM, private data center, or public cloud — without reconfiguration.
Physical analogy: A shipping container holds goods of any type in a standardized box. The shipping company doesn't care what's inside — only that the box fits the truck, ship, or crane. Similarly, the container runtime doesn't care what the app does — only that the image fits the container format.

Key Properties

Self-Contained
Everything the application needs — runtime, libraries, configuration — is packaged inside. No external dependencies on the host environment. The container image is the complete deployment unit.
OS-Level Virtualization
Containers virtualize at the OS level (not hardware level like VMs). They share the host OS kernel and use a fraction of the memory a full VM would require — making them extremely lightweight.
Run Anywhere
Same container image runs identically on Linux, Windows, Mac, on a developer's laptop, a VM, on-premise data center, or any public cloud. No environment-specific reconfiguration needed.
2 · Three Deployment Eras
Traditional Deployment Apps run directly on physical servers. No resource boundary between applications — resource-hungry apps starve others. No isolation, serious portability challenges.
Virtualized Deployment Multiple VMs run on a physical server via a hypervisor. Each VM has its own full guest OS. Better isolation, scalability, resource utilization — but each VM is a full system with its own OS overhead.
Container Deployment Containers share the host OS kernel and run on a container runtime. Each container has its own filesystem, CPU/memory share, and process space — but no full guest OS. Extremely lightweight, highly portable, decoupled from underlying infrastructure.
Container trade-off: Containers have "relaxed isolation" compared to VMs — they share the OS kernel. This makes them lighter but means a kernel vulnerability can potentially affect all containers on that host. VMs offer stronger isolation because each has its own kernel.
3 · Key Benefits of Containerization
Separation of Responsibilities
Developers focus on application logic and dependencies; IT operations teams focus on deployment and management — neither needs to deeply understand the other's domain. The container boundary is the interface.
Workload Portability
Containers run on Linux variants, Windows, Mac, VMs, physical machines, on-premise, and any public cloud. Enormously higher portability than traditional deployments — addressing one of the oldest challenges in IT.
Application Isolation
Containers virtualize CPU, memory, and network at the OS level, giving each application a logically isolated view. Applications cannot accidentally interfere with each other's resources or files.
Benefit
Agile Development
Developers avoid environment dependency concerns entirely — the container image IS the environment. Speeds up development cycles and eliminates "works on my machine" problems.
Benefit
Efficient Resource Use
Containers use only the computing resources the application actually needs. No guest OS overhead. More applications can run on the same hardware compared to VMs.

Virtual Machines

Memory footprintLarge — full OS in RAM
IsolationStrong — separate kernels
Startup timeSlow — full OS boot
PortabilityModerate
Containers
Virtualization levelOS level — shared kernel
Guest OSShares host OS kernel — no full guest OS
Memory footprintFraction of VM memory — very small
IsolationRelaxed — shared kernel is a risk surface

PortabilityVery high — decoupled from infrastructure
Containers and VMs together: These are not mutually exclusive. In practice, containers often run inside VMs — the VM provides strong isolation between tenants, while containers provide lightweight, fast deployment within each tenant's VM.
5 · Kubernetes Overview
Kubernetes: A portable, extensible, open-source platform for managing containerized workloads and services that facilitates both declarative configuration and automation. Originally developed by Google, became open-source (~2014). Name means "helmsman" or "pilot" in Greek.

Key Characteristics

Property
Operates at Container Level
Kubernetes manages containers and container groups (pods), not hardware. It provides PaaS-like features — deployment, scaling, auto-balancing, logging and monitoring integration — but is not a monolithic PaaS: these are optional and pluggable.
Property
Not Monolithic
Default solutions in Kubernetes are optional and pluggable. It provides building blocks for developer platforms while preserving user choice and flexibility — a developer can plug in their own logging, monitoring, or alerting solution.

Kubernetes Cluster Architecture

Kubernetes cluster: A set of worker machines called nodes that run containerized applications. Every cluster has at least one worker node. Worker nodes host pods — the smallest deployable units, each containing one or more containers.
Cluster component
Worker Nodes
The machines (physical or virtual) that host pods containing application workload components. Multiple nodes provide the compute capacity of the cluster. Key node components: kubelet, kube-proxy.
Cluster component
Control Plane
Manages the worker nodes and pods in the cluster — scheduling, scaling, fault detection, and overall cluster state. In production, the control plane runs across multiple computers for fault tolerance and high availability. Key components: scheduler, API server (kube API).
6 · Docker Overview
Docker: An open platform for developing, shipping, and running applications. Provides a sandbox process isolated from all other processes on the host machine — the container.
Docker concept
Container Image
A lightweight, standalone, executable package that includes everything needed to run the application: code, runtime, system tools, libraries, settings. The image is the static blueprint; the container is its running instance.
Docker concept
Docker Engine
The runtime that executes containers from images. Available for Linux and Windows. Container images become containers when run on the Docker Engine — same image, same behavior regardless of infrastructure.
Docker concept
Container Lifecycle
A container is a runtime instance of an image. Containers can be created, started, stopped, moved, and deleted using the Docker API or CLI. Each container runs as an isolated process separate from the host and other containers.
Docker concept
Isolation and Security
Docker provides strong default isolation capabilities — each container is an isolated sandbox. Applications inside containers are secured from each other and from the host environment.
Summary
Containers: Lightweight OS-level virtualization. Packages code + dependencies into a self-contained, portable unit. Shares host OS kernel — no full guest OS required.
Three eras: Traditional (bare metal, no isolation) → Virtualized (VMs with hypervisor, full guest OS, strong isolation) → Container (shares kernel, OS-level isolation, extremely lightweight and portable).
Three key benefits: Separation of responsibilities (developers vs. ops), workload portability (run anywhere), application isolation (logically separated process spaces).
Kubernetes: Open-source orchestration platform for containerized workloads. Cluster = control plane + worker nodes + pods. Provides scheduling, scaling, self-healing, and service discovery. Not monolithic — components are pluggable.
Docker: Container runtime platform. Container image = static package (code + runtime + libraries). Docker Engine executes images as isolated container processes. Industry-standard container format and the most widely used runtime.
Containers vs. VMs: Containers share the OS kernel (lighter, faster, more portable) while VMs run full guest OSes (heavier, stronger isolation). Both are used together in production — VMs for tenant isolation, containers for application packaging.
