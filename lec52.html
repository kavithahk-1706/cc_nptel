Lecture 52 HIGH priority

Serverless Computing — I

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Introduces Serverless Computing — an emerging paradigm where developers write business logic as functions without managing infrastructure. Covers the two core service models (FaaS and BaaS), how serverless works (event-driven, stateless containers, horizontal scaling), and its key challenges. High exam relevance: definitions, service model distinctions, and challenges are likely to appear.

1 · What is Serverless Computing?
Serverless Computing: A method of providing backend services on a used (pay-per-use) basis. The serverless provider allows users to write and deploy code without worrying about underlying infrastructure. Servers still exist — the term "serverless" means the developer has no visibility into or responsibility for the server layer.
Core goal: Separate infrastructure management from application development. Developers focus exclusively on business logic; the cloud provider handles container creation, deployment, provisioning, orchestration, and scaling.
No Infrastructure Management
Developers do not provision VMs, configure OS, manage containers, or monitor infrastructure. The serverless provider handles all operational aspects including container orchestration — analogous to abstracting the server layer entirely.
Event-Driven Execution
Applications are granular and triggered by events — client requests, data streams, external system events, or scheduled triggers. Functions are not constantly active; the FaaS platform listens for events and instantiates the function only when triggered.
Pay-Per-Use Billing
Users are billed only for the resources consumed during function execution — not for idle infrastructure. A non-active serverless function costs nothing. This is a finer-grained billing model than IaaS/PaaS where you pay for provisioned capacity.
Key distinction from IaaS/PaaS/SaaS: In traditional cloud models, developers still manage server provisioning, OS selection, scaling configuration, and container orchestration. Serverless abstracts all of this — the developer only provides the function logic.
2 · Two Service Models of Serverless
Serverless computing encompasses two categories: Backend as a Service (BaaS) and Function as a Service (FaaS). Both eliminate server management, but they differ in what the developer provides.
Backend as a Service (BaaS)
What it replacesServer-side components replaced with managed third-party services
Developer roleWrites and maintains all application logic in the frontend; all backend infrastructure is outsourced
What's managedRemote authentication, database management, cloud storage, hosting — all at the backend
ExampleGoogle Firebase — a fully managed database that connects seamlessly to web/mobile applications; manages data components on the user's behalf
Developer concernApplication logic and frontend only — backend services are consumed via APIs
Function as a Service (FaaS)
What it replacesFull infrastructure management; developer submits code as discrete functions
Developer roleWrites small, stateless functions that each describe a part of the overall application workflow
What's managedResource lifecycle, event-driven execution, horizontal scaling, container creation, deployment, provisioning
ExampleAWS Lambda, Google Cloud Functions, Microsoft Azure Functions — user submits function; provider runs it in a shared runtime when triggered
Developer concernBusiness logic as functions and how functions interconnect in workflows; nothing about servers
Key insight: Serverless = BaaS + FaaS. BaaS replaces server-side components with managed services. FaaS allows developers to run event-driven code without managing the execution environment. Together they eliminate all infrastructure concerns from the developer's scope.
3 · Function as a Service — How It Works
FaaS concept
Small, Stateless Functions
Each function describes a small part of the overall application. User provides these small stateless functions to the cloud provider, which manages the operational aspects of running them. Functions are composed together to realize complex application workflows.
FaaS concept
Event-Triggered Execution
Functions are not constantly active. The FaaS platform listens for events and instantiates the function only when triggered. Trigger types: client requests, events produced by external systems, data streams, scheduled timers. Example: a camera application function triggered by detected object movement, not by constant polling.
FaaS concept
Horizontal Scaling by Provider
The FaaS provider is responsible for horizontally scaling function execution in response to the number of incoming events. Provider runs multiple function instances in parallel as demand increases. Developer does not configure scaling — it is automatic and transparent.
FaaS concept
Execution Time Limits
Functions are not designed for long-running tasks. Execution time is typically limited — for example, AWS Lambda has a ~15-minute limit. Functions run in isolated, nearly stateless containers that may be ephemeral (lasting only for one invocation). Designed for short, discrete units of work.
xCamera example: A video camera application that uses cloud functions and workflows to edit, transform, and encode videos with low latency and minimal cost. Many tasks (frame-by-frame processing, encoding, transmission) can be executed concurrently via parallel function invocations — improving performance through parallelization, managed by the FaaS provider.
4 · Challenges of Serverless Computing
Challenge
Asynchronous Calls
Asynchronous calls to and between serverless functions increase system complexity. Remote API calls normally follow a synchronous request-response model and are easier to implement. Asynchronous function interactions require more complex coordination logic and are harder to debug.
Challenge
Function Calling Function
When one function synchronously calls another, you lose isolation between features, debugging becomes more complex, and billing increases (paying for two functions running simultaneously). The composition of functions into complex chains introduces overhead that negates some serverless benefits.
Challenge
Shared Code Between Functions
Code shared between multiple functions creates fragility. If shared code is changed, it may break existing serverless functions that depend on it — without clear visibility into what is affected. Managing shared code versioning across many functions is non-trivial.
Challenge
Image Size Limits
Platforms impose image size limits (AWS Lambda: 50 MB). Larger images take longer to boot (cold start / warmup time). Using too many libraries increases package size and risks hitting this limit. There is a tension between feature richness and startup performance.
Challenge
Too Many Technologies
The flexibility of serverless (any language, any framework, any library) can lead to adopting too many technologies within one project. This adds maintenance complexity and increases the skill requirements for team members — specialists in many different tech stacks may be needed.
Challenge
Too Many Functions
Since non-active functions cost nothing, there is a temptation to create new functions instead of updating existing ones when requirements change. This decreases maintainability and system understandability — especially problematic during project handovers. Function sprawl makes the overall application architecture hard to reason about.
5 · Popular Serverless Platforms
AWS Lambda Google Cloud Functions Microsoft Azure Functions Google Firebase (BaaS)
All three major cloud providers offer FaaS platforms. Open-source alternatives also exist. Google Cloud additionally offers virtual servers, managed databases, and storage services alongside Cloud Functions as a complete serverless ecosystem.
Summary
Serverless Computing: A paradigm where the cloud provider manages all infrastructure — containers, deployment, provisioning, orchestration, scaling — so developers can focus purely on business logic. Servers still exist; the developer just doesn't see or manage them.
Two models: BaaS (backend components replaced by managed third-party services; developer writes only frontend logic) and FaaS (developer submits small stateless functions; provider handles execution, scaling, and lifecycle).
FaaS mechanics: Functions are small, stateless, event-triggered (client requests, data streams, external events), not constantly active, with limited execution time (e.g., AWS Lambda: ~15 min). Provider horizontally scales by running multiple function instances in parallel.
BaaS example — Google Firebase: A fully managed database directly usable from web/mobile applications without any server-side setup. The developer connects to it as a service; Firebase manages all backend data operations.
Key challenges: Asynchronous function composition complexity, function-calling-function costs and debugging difficulty, shared code fragility, image size limits (50 MB on Lambda), technology sprawl, and function proliferation reducing system understandability.
Popular platforms: AWS Lambda, Google Cloud Functions, Microsoft Azure Functions — the three dominant FaaS implementations across major cloud providers.
