Lecture 45 HIGH priority

VM Migration — Basics and Migration Strategies

Prof. Soumya Kanti Ghosh · Dept. of Computer Science and Engineering, IIT Kharagpur

Covers the motivation for VM migration in cloud data centers, the two broad categories (cold/non-live vs. hot/live), what state must be moved (CPU, memory, disk, network, I/O), and the three memory migration primitives: push, stop-and-copy, and pull. Then details the pre-copy and post-copy live migration strategies. Foundational for understanding cloud resource management and SLA compliance.

1 · Why VM Migration?
VM migration: The process of moving a running application or VM from one physical host server to another — while optionally preserving continuity of service.
Reason
Load Balancing
Allocation and deallocation of VMs over time leaves some servers heavily loaded and others lightly loaded. Migration redistributes VMs for fair workload distribution across all servers.
Reason
Server Maintenance
When a physical server requires maintenance or shutdown, all VMs running on it must be migrated to other servers transparently — the customer's SLA must still be respected and the application must keep running.
Reason
Power Consolidation
If five VMs are spread across five servers but could run on one or two, migrate and consolidate them, then put underutilized servers into low-power mode. Reduces operational cost during low-demand periods.
Reason
QoS Violation
When a CSP fails to meet the agreed SLA quality, the user may migrate their VM to another service provider — migration can cross provider boundaries, not just server-to-server within one DC.
Reason
Fault Tolerance
In anticipation of or response to failure, VMs can be migrated from a failing or at-risk data center to another where they can continue executing safely.
Migration cost: Every migration has communication overhead (moving memory state across the network) and downtime cost. Excessive downtime violates SLA — the CSP pays a penalty and risks reputational damage.
2 · Cold vs. Live Migration
Cold / Non-Live Migration
VM state during migrationSuspended or shut down — not providing service
DowntimeHigh — proportional to VM memory size
Implementation complexityLow — simpler to implement and reason about
SuitabilityBatch or offline workloads where downtime is acceptable
Risk for real-time appsSevere service quality degradation — unacceptable for live services
Hot / Live Migration
VM state during migrationContinues executing and providing service throughout
DowntimeMinimal — brief stop-and-copy phase only
Implementation complexityHigh — requires careful state tracking and dirty page management
SuitabilityReal-time applications, live broadcasts, online computation
User experienceSeamless — user is practically unaware migration occurred
Non-live migration downtime: For a large VM, downtime is proportional to physical memory size. If the VM is serving live users, this downtime causes severe SLA degradation.
3 · What Must Be Migrated?

CPU Context and Main Memory

CPU context (register state, process state) and main memory contents (RAM) are the two critical items that must always be migrated. Without these, the VM cannot resume execution at the destination.

Disk Storage

Disk scenario
Network-Attached Storage (NAS)
If both source and destination hosts can access the same NAS server, disk migration is trivial — just reconnect the network path from the source server's port to the destination server's port. The data itself does not move.
Disk scenario
Local Disk
If disk is local to the source host, disk data must be mirrored or moved to the destination. More challenging — disk data is large and copying it takes time and bandwidth.

Network

If source and destination are on the same LAN: migrate the IP, advertise the new MAC→IP mapping via ARP reply, and switches learn the new MAC location. Network packets are redirected to the new location with only transient losses. If different LANs, proxying and other mechanisms are needed.

I/O Devices

Virtual I/O devices are easier to migrate — they are software abstractions and can be re-instantiated on the destination. Physical device assignment (direct passthrough of a physical device to a VM) is harder — the physical device must now be connected to a different server, which may not always be possible.
4 · Memory Migration Primitives
Push
Source VM continues running. Memory pages are pushed to the destination across the network. Pages modified during pushing (dirty pages) must be re-sent in subsequent rounds. Source keeps running throughout — no suspension.
Stop-and-Copy
Source VM is stopped (suspended). Remaining dirty pages and CPU state are then copied to the destination. VM execution is resumed at the destination. Simple, but downtime is proportional to total physical memory size.
Pull (on-demand)
New VM starts executing at the destination with an empty memory. When it accesses a page not yet copied, it triggers a page fault — the missing page is pulled across the network from the source VM on demand. Only frequently accessed pages need to be transferred.
Pure stop-and-copy limitation: Downtime and total migration time are both proportional to the amount of physical memory allocated to the VM. For large VMs running live services, this outage is unacceptable.
5 · Pre-Copy Live Migration
Core idea: Reduce downtime by copying most of memory while the source VM is still running, then perform only a brief stop-and-copy for the remaining dirty pages.

Phases of Pre-Copy

PhaseWhat happensSource VM state
Pre-copy roundsActive memory pages are copied iteratively to the destination, round by round. Pages modified during copying (dirty pages) are flagged and re-sent in the next round.Running — still serving users
Pre-copy terminationCopying stops when a threshold is met: (a) number of rounds executed reaches N, (b) total memory transmitted exceeds a threshold, or (c) number of dirty pages in the previous round drops below a threshold (indicating convergence).Running
Stop-and-copyVM execution is suspended at source. Remaining dirty pages and CPU state are copied to the destination. This is the actual downtime window — kept short because most memory is already at the destination.Suspended (downtime)
RestartVM is restarted at the destination server and resumes normal execution.Running at destination
Dirty pages: A "dirty page" is any memory page that was modified at the source after it was already copied to the destination. It must be re-transmitted to keep the destination copy consistent. If pages are modified faster than they can be copied (memory-intensive workloads), convergence may be slow.
Caveat: Network delay is assumed minimal in the standard pre-copy model. Migrating across geographically separated data centers — with high latency — significantly increases the challenge and overhead of live migration.
6 · Post-Copy Live Migration
Core idea: Start the VM at the destination immediately with only CPU state copied. Copy memory pages on-demand (pull) as the destination VM accesses them. Only actually-needed pages are transferred.

Post-Copy Phases

PhaseWhat happens
Stop source VMSource VM is stopped and CPU state is copied to the destination node. Unlike pre-copy, no memory is pre-transferred.
Restart at destinationDestination VM restarts with CPU state restored but with an empty memory image.
On-demand memory copyAs the destination VM executes, any memory page access that cannot be satisfied locally triggers a pull from the source VM across the network. Only required pages are fetched.
Background copyRemaining pages can also be proactively pushed in the background (not strictly on-demand) to reduce future page faults.
Post-copy advantage: Most pages of a VM are never accessed again after migration — post-copy avoids transferring unused pages entirely. Only the working set is truly moved.
Post-copy risk: If the source host fails before all demanded pages have been fetched, the destination VM cannot recover the missing pages. Pre-copy is safer because most state is already at the destination before the VM switches over.
7 · Key Migration Metrics
Metric
Downtime
Total time during which the service is unavailable to users. Goal: minimize. In pre-copy live migration, only the stop-and-copy phase contributes to downtime. In non-live migration, the entire migration duration is downtime.
Metric
Total Migration Time
Time from start of migration process to when the VM is fully operational at the destination and the source VM is released. Includes all pre-copy rounds + stop-and-copy + restart. Longer migration time = longer resource contention and overhead.
Metric
Resource Contention
Migration consumes CPU and network bandwidth at both source and destination. This contention can degrade the performance of other VMs on those hosts and may itself trigger further SLA violations.
Metric
SLA Compliance
If downtime or performance degradation during migration exceeds SLA thresholds, the CSP must pay a penalty. Poor migration management therefore has direct financial consequences beyond technical overhead.
Summary
VM Migration: Moving a running VM from one physical host to another. Required for load balancing, maintenance, power consolidation, QoS enforcement, and fault tolerance.
Two categories: Cold/non-live (VM suspended during migration — simple, high downtime) vs. hot/live (VM continues running — complex, minimal downtime).
What moves: CPU context and main memory (always critical); disk (trivial if NAS, harder if local); network (straightforward on same LAN via ARP); I/O (virtual devices easy, physical passthrough hard).
Three memory primitives: Push (source running, copy pages, re-send dirty); Stop-and-copy (suspend source, copy all, restart — simple but high downtime); Pull (start at destination, fetch pages on demand).
Pre-copy live migration: Iterative push rounds while source runs, then a short stop-and-copy for remaining dirty pages, then restart at destination. Converges when dirty page count drops below threshold.
Post-copy live migration: Stop source, copy only CPU state, restart destination VM immediately, fetch memory pages on-demand as needed. Efficient (only working set transferred) but risky if source fails during transfer.
